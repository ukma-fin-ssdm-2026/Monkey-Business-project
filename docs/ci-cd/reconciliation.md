# Перевірка автоматичного та ручного підрахунку

Використання ШІ: Codex — порівняння API-даних із попереднім командним звітом і підготовка контрольних прикладів.

Попередні результати Етапу 2 збережено без змін у [manual-baseline/dora-summary.md](evidence/manual-baseline/dora-summary.md) і [manual-baseline/metrics-raw.md](evidence/manual-baseline/metrics-raw.md). Їхній вихідний [JSON 83 запусків](evidence/main-runs-2026-11-01-to-2026-11-14.json) також залишено. Актуальна основна вибірка — [api-snapshot.json](evidence/api-snapshot.json).

## Чому 25 комітів замість 23

Попередній звіт називав 01.11–14.11.2026 **київським** періодом, але JSON задавав `[2026-11-01T00:00:00Z, 2026-11-15T00:00:00Z)`. Правильні межі цього локального періоду — `[2026-10-31T22:00:00Z, 2026-11-14T22:00:00Z)`.

Через двогодинне зміщення пропущено два коміти:

| Коміт / PR | Створення CI, UTC | Створення CI, Київ | Workflow |
|---|---|---|---:|
| [`e5db88e`, #192](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/192) | 31.10 23:05:53 | **01.11 01:05:53** | 5 |
| [`16e54e1`, #193](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/193) | 31.10 23:20:10 | **01.11 01:20:10** | 5 |

Усі 83 ID попередньої вибірки є в новому snapshot. Додано лише ці 10 запусків. Вони зелені; іншого вилучення даних немає.

## Порівняння

Стовпець «Ті самі 23 SHA» перераховано новим алгоритмом після фільтрації API-snapshot за SHA старої вибірки. Це дозволяє відокремити зміну періоду від зміни точності формул.

| Показник | Попередній звіт | Ті самі 23 SHA, точні API-поля | Правильний київський період, 25 SHA |
|---|---:|---:|---:|
| Workflow-запуски | 83 | 83 | 93 |
| Зелені коміти | 23 | 23 | 25 |
| Deployment frequency / тиждень | 11,5 | 11,5 | **12,5** |
| Lead time, середнє, хв | 107,8 | 107,8123 | **107,4367** |
| Lead time, медіана, хв | 23,2 | 23,1667 | **24,9667** |
| Change fail rate | 0% | 0% | **0%** |
| Recovery time | н/д | н/д | **н/д** |
| До створення CI, сума, хв | 2104,6 | 2104,0000 | **2298,8500** |
| Початкова черга, сума, хв | 146,8 | 147,2833 | **148,6333** |
| Інтервал виконання SHA, сума, хв | 228,3 | 228,4000 | **238,4333** |
| Медіана виконання SHA, хв | 1,5 | 1,4667 | **1,8000** |
| Медіана виконання одного workflow, хв | Не обчислено окремо | 0,9167 | **0,9000** |

Середнє й медіана lead time для старих 23 SHA підтверджуються після округлення. Для малих розбіжностей сум часу старий JSON не містить jobs і не дозволяє відновити точний алгоритм попереднього розрахунку. Новий результат бере секунди безпосередньо з `jobs.started_at` / `jobs.completed_at`, не підсумовує округлені рядки й не підміняє завершення job полем `updated_at`. Наприклад, для `124ce67` останній job закінчився о `10:03:11Z`, тоді як `updated_at` запуску CI — `10:03:12Z`. Стверджувати, що всі старі розбіжності спричинені лише округленням, на підставі старого JSON не можна.

## Виправлення інтерпретації

1. **Дні розгортань визначаються завершенням зеленого стану.** Актуальні кількості: 01.11 — 6, 02.11 — 5, 07.11 — 4, 08.11 — 7, 09.11 — 3. На решті днів — 0. Попередній розподіл 7/3/4/7/2 не збігається з локальними датами завершення: зокрема PR #198 завершився вже 02.11, а #227 — 09.11.
2. **Порівняння CircleCI робиться з окремими workflow.** Попередні 1,5 хв і 103,2 хв описували інтервали всіх workflow одного SHA. Для 93 окремих workflow медіана — 0,90 хв, максимум — 3,80 хв.
3. **Категорія частоти:** 12,5 / тиждень = 1,79 / день за повним 14-денним вікном. За середньою частотою це «від щогодини до щодня», 22,7% за таблицею завдання. Нерівномірність доставки показана окремо й не приховується категорією. Старі 11,5 / тиждень також не обґрунтовують категорію «від щодня до щотижня», якщо класифікувати саме середню частоту.
4. **Час до CI не дорівнює часу review.** 85,59% lead time — від першого коміту до створення CI; цей інтервал включає розробку та очікування. Для твердження про повільне review потрібно додатково виміряти його етапи.

## Незалежні контрольні приклади

Усі timestamps нижче — UTC, без округлення. Вони збережені у snapshot разом із посиланнями на PR і запуски.

| SHA / PR | Перший коміт | CI створено | Перший job | Останній job | Ручний результат |
|---|---|---|---|---|---|
| `124ce67` / #194 | 01.11 00:04:18 | 01.11 10:02:12 | 01.11 10:02:14 | 01.11 10:03:11 | Черга **2 с**, виконання **57 с**, lead **9 год 58 хв 53 с** |
| `268e753` / #195 | 01.11 16:47:48 | 01.11 16:57:06 | 01.11 16:57:09 | 01.11 17:10:58 | Черга **3 с**, виконання **13 хв 49 с**, lead **23 хв 10 с** |
| `3184d4f` / #198 | 01.11 19:45:07 | 01.11 20:47:02 | 01.11 21:13:22 | 01.11 22:56:31 | Черга **26 хв 20 с**, виконання **1 год 43 хв 9 с**, lead **3 год 11 хв 24 с** |

Для #198 об'єднання інтервалів усіх jobs займає **8 хв 27 с**. Усередині 103 хв 9 с лишається **94 хв 42 с**, протягом яких жоден job цього SHA не виконувався. Отже, довгий інтервал не є доказом повільного тесту. Очікування спільних раннерів — правдоподібне пояснення, але дані цього репозиторію не показують навантаження інших команд.

Загальні інваріанти перевірки: 25 унікальних SHA, 93 унікальні run ID, кожен `attempt = 1`, усі conclusions `success`, усі PR зв'язані зі своїм merge SHA, 25 додатних lead time. Сума частин lead time — **2685,9167 хв**, частки разом — **100%**.

## Повторення порівняння для 23 старих SHA

З кореня репозиторію виконайте Python-код у наявному середовищі:

from pathlib import Path
from scripts.calculate_ci_metrics import calculate

result = calculate(data)
print(result["lead_time_minutes"])
print(result["lead_time_parts"])
