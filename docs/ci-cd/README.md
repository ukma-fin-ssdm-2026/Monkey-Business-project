## Запуск

Потрібен Python 3.11+; розрахунок використовує стандартну бібліотеку. На Windows за відсутності бази часових поясів встановіть `python -m pip install tzdata`. У наявному `.venv` проєкту вона вже є.

Скрипт читає REST API GitHub. Авторизація: `GH_TOKEN` / `GITHUB_TOKEN`, або наявна сесія `gh auth login`; необов'язковий `--git-auth` використовує збережені облікові дані Git для `github.com`. Секрети не записуються до доказів чи звітів. Для приватного репозиторію потрібні права читання Actions, Contents, Pull requests і Checks (для annotations).

З кореня репозиторію, у цьому Windows-середовищі:

```powershell
.\.venv\Scripts\python.exe scripts/calculate_ci_metrics.py --repo ukma-fin-ssdm-2026/Monkey-Business-project --from 2026-11-01 --to 2026-11-15 --timezone Europe/Kyiv --git-auth
```

З активованим Python та авторизацією через `gh` або змінну середовища:

```bash
python scripts/calculate_ci_metrics.py --from 2026-11-01 --to 2026-11-15 --timezone Europe/Kyiv
```

Відтворення результату з уже збережених API-доказів, без мережі:

```powershell
.\.venv\Scripts\python.exe scripts/calculate_ci_metrics.py --offline
```

`--to` — **виключна** верхня межа. Параметри періоду й workflow при `--offline` беруться зі snapshot, а не змінюють його. Для окремого результату використайте `--output <каталог>`; для іншого snapshot — `--evidence <файл>`. Параметр `--workflow` можна повторювати, щоб явно задати інший перелік workflow.

Збір і перерахунок запускаються **лише локально за командою**. Скрипт виконує GET-запити, не створює CI-запусків і не займає спільні раннери. Workflow або розклад для цього бонусу не додано.

## Межі й одиниця вимірювання

- Основна вибірка: `2026-11-01 00:00:00` ≤ створення CI < `2026-11-15 00:00:00`, **Europe/Kyiv**. У UTC це `[2026-10-31T22:00:00Z, 2026-11-14T22:00:00Z)`.
- Враховуються `push` на `main`. `pull_request` і ручні запуски не входять до основних метрик.
- Workflow: `CI`, `Static analysis`, `Lab07 card ordering`, `Lab08 characterization tests`, `Generate and Deploy API Docs`. Два останні запускаються умовно за шляхами; workflow, якого не було для коміту, не вважається помилкою.
- Одна зміна — один повний `head_sha`. Враховуються всі запуски вибраних workflow цього SHA; повтори завантажуються через endpoint кожної `attempt`.
- Скрипт збирає всі сторінки API та додатково отримує весь набір workflow за кожним SHA. Якщо запит перевищує обмеження API 1 000 запусків, він завершується з повідомленням про необхідність звузити період, замість мовчазного обрізання даних.
- Це вибірка за **створенням CI**; лише завершення до кінця вікна формують результати. Запуск, створений раніше початку вікна, не входить до цієї когорти. У поточних даних немає незавершених або граничних запусків, які змінюють результат.
- Зелений стан настає, коли всі враховані workflow коміту мають `success`. Це наближення готовності до випуску за умовою лабораторної, а не фактичне production-розгортання.
- Червона зміна має хоча б один `failure`, `timed_out`, `action_required`, `startup_failure` або `stale`. Час виявлення червоного стану — завершення першого такого workflow. У поточній основній вибірці таких записів немає.
- Успішний перезапуск не стирає попередню невдачу: SHA рахується один раз у знаменнику CFR і один раз як невдала зміна; його перший зелений стан може також дати одне розгортання. Повторний зелений стан того самого SHA не збільшує deployment frequency.
- `cancelled`, `skipped`, `neutral` не перетворюються на успіх чи збій: це окрема категорія `other`, яка входить до всіх завершених записів. Незавершені набори workflow вилучаються зі знаменника CFR й показуються окремо. У поточній вибірці всі 25 записів зелені.

## Формули й часові поля

Для кожного workflow:

```text
queue = min(jobs.started_at) - run.created_at
execution = max(jobs.completed_at) - min(jobs.started_at)
```

Враховуються jobs, які не мають статусу `skipped`. `updated_at` не підміняє час завершення останнього job. Якщо завершений запуск не має часових даних jobs, скрипт явно попереджає про fallback до `updated_at`, а queue/execution залишає невідомими. Для повторних спроб queue є `null`: `created_at` належить першому запуску й не визначає час постановки повтору в чергу.

Для одного SHA початкова черга — від найранішого створення workflow до першого job; інтервал виконання — від першого job до завершення всіх врахованих workflow. Тривалості паралельних jobs не додаються. Інтервал може містити очікування інших jobs і workflow.

Додатково `active_job_minutes` — довжина об'єднання інтервалів jobs, а `internal_idle_minutes` — час між першим і останнім job, коли жоден job цього SHA не виконувався. Це показники часової шкали API, не вимірювання CPU чи доведення того, хто займав інші раннери.

| Метрика | Формула |
|---|---|
| Deployment frequency | Число SHA з першим зеленим станом / тривалість вікна у тижнях |
| Change lead time | Перший зелений стан `main`, який містить зміну, мінус `authored_at` першого коміту злитого PR; середнє й медіана |
| Change fail rate | SHA з невдачею / всі завершені SHA × 100% |
| Failed deployment recovery time | Від першого червоного стану SHA до наступного зеленого стану на `main`; середнє й медіана |

PR зв'язується з SHA через `commits/{sha}/pulls`, з перевіркою `merged_at`, base `main` і `merge_commit_sha`. Перший коміт береться з порядку відповіді `pulls/{number}/commits`, його авторська дата зберігається без округлення. Для прямого коміту початком є авторська дата цього коміту. Неповна історія PR або неоднозначний зв'язок спричиняють явну помилку.

Для зміни, що стала доступною в іншому зеленому коміті, ancestry підтверджується `compare/{change_sha}...{green_sha}`. Це також враховує випадок, коли наступний коміт завершує CI раніше за власний повільний запуск попереднього SHA. Lead time включає очікування виправлення у разі збою. `lead_queue_minutes` і `lead_execution_minutes` описують шлях до першого зеленого коміту, що містить зміну, окремо від часової шкали власних workflow SHA; початком виконання є найраніший job вихідного або цього зеленого коміту. Відновлення шукається за наступним зеленим станом, як вимагає умова; невідновлені збої показуються окремо й не заповнюються нулями.

Повний lead time розділяється на час **до створення CI**, початкову чергу і час від першого job до зеленого стану. Перша частина містить розробку, review, очікування злиття та запуску CI; називати її лише очікуванням review некоректно. Усі частки основної вибірки рахуються від суми повних lead time тих самих 25 змін.

## Перевірка

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_ci_metrics.py --no-cov -q
.\.venv\Scripts\python.exe -m black --check scripts/calculate_ci_metrics.py tests/test_ci_metrics.py
.\.venv\Scripts\python.exe -m flake8 scripts/calculate_ci_metrics.py tests/test_ci_metrics.py
```

Тести використовують синтетичні приклади й не змішуються з реальними доказами. Перевірено паралельні workflow, відновлення після повтору, невідновлений збій, відсутність збоїв, прямий коміт, ancestry, чергу, внутрішні паузи, пагінацію та межі періоду. Ручні контрольні приклади наведено в [reconciliation.md](reconciliation.md).

Перевірено 15.11.2026: **21/21 тест автоматизації**, black і flake8 для нових Python-файлів; повний Python-набір — **287 passed, 12 skipped**, покриття застосунку **94,07%**. Пропущені тести потребують окремої PostgreSQL через `TEST_DATABASE_URL`. Показник покриття належить `src/api`, а не скрипту метрик.

У цьому Windows-середовищі повний прогін виконано з UTF-8 і окремим tmp-каталогом, оскільки типовий системний каталог pytest був недоступний, а системне кодування cp1252 не читало українські коментарі:

```powershell
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m pytest --basetemp .pytest_cache/lab10-verification-20261115-02 -q --tb=short
```

Повторний offline-розрахунок підтверджує і листопадову вибірку, і жовтневий інцидент. Окрема незалежна перевірка підтвердила унікальність 93 ID, відповідність 25 PR своїм merge SHA, середнє/медіану з timestamps jobs і суму часток 100%.

`pre-commit run --all-files` також виконано: він виявив попередні зауваження форматування та flake8 у сторонніх тестах (`test_mcp_server.py`, `test_mentors.py` тощо). Автоматичне переформатування цих файлів скасовано, щоб зберегти межі внеску Лаб10. Для повного набору файлів цього внеску окремо пройдено **black, flake8, bandit і detect-secrets**. Нові спрацювання detect-secrets у JSON перевірено через `git cat-file -t`: це публічні commit SHA, їх точково позначено `is_secret: false` у `.secrets.baseline`. Правила сканера й перевірка решти файлів залишаються активними.
