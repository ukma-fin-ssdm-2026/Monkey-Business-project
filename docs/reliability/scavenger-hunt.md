# Resilience Scavenger Hunt (Лабораторна 9)

Роль: **аналітик відмов**. Аналіз виконано в поточному коді проєкту
`Monkey-Business-project`. Для кожної знахідки наведено категорію A–E,
ланцюг `fault → error → failure`, критичність і потенційний вплив.

## R1. Широкий `except Exception` у валідації URL

**Код:** `src/api/validators.py:36-44`

```python
try:
    parsed = urlparse(cleaned)
    if parsed.scheme.lower() not in ALLOWED_SCHEMES:
        return False
    return _is_safe_host(parsed.hostname)
except Exception:
    return False
```

**Fault:** валідатор перехоплює будь-який виняток, включно з непередбаченою
помилкою в майбутній логіці. **Error:** дефект усередині перевірки
перетворюється на звичайне `False` без діагностики. **Failure:** користувач
отримує помилку валідації або не може зберегти коректне посилання.

Це небезпечно через мовчазне маскування програмних помилок. Для некоректного
URL потрібне безпечне значення, але не можна приховувати помилки валідатора.
Потенційний вплив — хибні відмови у створенні або редагуванні картки.

## R2. `fetch` не має клієнтського тайм-ауту

**Код:** `src/frontend/src/api/client.ts:82-89`

```typescript
res = await fetch(`${API_BASE}${path}`, {
  method,
  headers,
  body: body !== undefined ? JSON.stringify(body) : undefined,
});
```

**Fault:** запит не має `AbortController` або іншого дедлайну. **Error:**
браузер очікує відповідь від завислого API або мережевого проксі. **Failure:**
інтерфейс залишається в стані завантаження, а користувач не отримує
керованого повідомлення про збій.

Потрібна швидка відмова з повідомленням «сервіс не відповідає», інакше
можливі завислі екрани, повторні кліки та накопичення невдалих запитів.

## R3. `JSON.parse` без обробки некоректного тіла відповіді

**Код:** `src/frontend/src/api/client.ts:100-101`

```typescript
const text = await res.text();
const data = text ? JSON.parse(text) : undefined;
```

**Fault:** клієнт припускає, що кожна непорожня відповідь є JSON. **Error:**
HTML reverse proxy, обрізане тіло або некоректний JSON викликає `SyntaxError`.
**Failure:** компонент отримує неочікуваний виняток замість типізованого
`ApiError`.

Потенційний вплив — незрозумілий збій під час 502/503 або помилки деплою.
Потрібно перехоплювати помилку розбору та повертати безпечне повідомлення.

## R4. Необмежений цикл завантаження карток

**Код:** `src/frontend/src/pages/BoardPage.tsx:17-27`

```typescript
while (true) {
  const page = await api.listCards(boardId, limit, offset);
  all.push(...page.items);
  if (all.length >= page.pagination.total || page.items.length === 0) break;
  offset += limit;
}
```

**Fault:** завершення циклу залежить тільки від коректного `total` і зміни
сторінок. **Error:** помилкова пагінація API, кеш або повторення тієї самої
сторінки не гарантує прогрес до умови виходу. **Failure:** екран дошки
завантажує сторінки без кінця, витрачає пам'ять і не показує результат.

Потрібні перевірка прогресу, максимальна кількість сторінок і повідомлення
про неповну відповідь.

## R5. Помилки допоміжних даних замінюються порожніми масивами

**Код:** `src/frontend/src/components/CardModal.tsx:86-88, 101`

```typescript
api.listLinks(boardId, card.id).then(setLinks).catch(() => setLinks([]));
api.listNotes(boardId, card.id).then(setNotes).catch(() => setNotes([]));
api.listMentors(boardId).then(setMentors).catch(() => setMentors([]));
```

**Fault:** catch-блоки втрачають саму помилку і встановлюють порожній стан.
**Error:** недоступні links, notes або mentors не відрізняються від ситуації
«даних справді немає». **Failure:** користувач бачить неповну картку та може
прийняти відсутність даних за коректний стан.

Це типовий silent failure. Потрібно зберігати стан помилки, логувати її без
секретів і дозволяти повторити завантаження.

## R6. Помилка запису OpenAPI може зупинити запуск сервісу

**Код:** `src/api/main.py:21-34`

```python
SPEC_PATH.parent.mkdir(parents=True, exist_ok=True)
with SPEC_PATH.open("w", encoding="utf-8") as f:
    yaml.dump(openapi_schema, f, sort_keys=False, allow_unicode=True)
```

**Fault:** операції каталогу та файлу не мають обробки `OSError` і записують
прямо в цільовий файл. **Error:** read-only filesystem або перерваний запис
дають виняток під час старту. **Failure:** API не запускається, хоча роутери
та база доступні, або специфікація залишається обрізаною.

Потрібно відокремити генерацію від критичного старту або використовувати
тимчасовий файл із атомарним rename та явним логуванням.

## R7. Синхронний email-виклик усередині транзакції

**Код:** `src/api/routers/mentors.py:170-184`

```python
invitation = repos.mentors.add(...)
_send_invitation_email(email, token, board_id)
return _to_mentor_out(invitation, email)
```

**Fault:** HTTP-виклик Mailtrap виконується до завершення транзакції запиту.
**Error:** повільний або недоступний провайдер утримує DB session та блокування,
а помилка надсилання відкочує створення запрошення. **Failure:** користувач
чекає до тайм-ауту, отримує 503 і не має ані листа, ані створеного
запрошення.

Це високий ризик через поєднання зовнішньої залежності та транзакції.
Потрібні обмежений тайм-аут, вузький catch, логування з request ID і
узгоджена стратегія швидкої відмови без коміту.

## R8. MCP login не перевіряє структуру JSON-відповіді

**Код:** `src/api/mcp_server.py:69-78`

```python
if response.status_code != 200:
    raise RuntimeError(...)
return response.json()["access_token"]
```

**Fault:** код перевіряє лише HTTP 200 і безпосередньо звертається до
`access_token`. **Error:** пошкоджена/змінена відповідь або не-JSON тіло
викликає `JSONDecodeError` чи `KeyError`. **Failure:** MCP-інструмент
завершується неструктурованим винятком і не виконує запит.

Потрібно перевірити JSON-схему, повернути явну конфігураційну або сервісну
помилку та не показувати сирі деталі провайдера.

## Висновок

Найвищий пріоритет мають R2, R4 і R7: вони можуть залишати основний
інтерфейс або критичний сценарій у стані очікування та створювати каскадне
навантаження. R1, R3, R5, R6 і R8 слід виправляти через контрольовані
помилки, явне логування та безпечні повідомлення. Виправлення 3–5
найкритичніших проблем і тести надійності мають бути описані окремо у
`docs/reliability/reliability-report.md`.
