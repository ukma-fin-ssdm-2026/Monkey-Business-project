# План тестування — Monkey Business

**Обсяг:** тестуємо права ментора та відкликання доступу, створення й упорядкування карток, посилання і коментарі; після взаємного огляду додано редагування картки (FR-008) та запрошення ментора (FR-012); окремо — SEC-3 та сценарій PERF-4. Поза обсягом: AI-асистент, нагадування, аналітика, підтримка, повний набір адміністративних функцій, доставка справжніх email та інші NFR.

**Критерії виходу:** план містить сценарії з критеріями прийняття, власниками та зв’язками з RTM; зауваження взаємного огляду враховано в плані й review-log.md; реалізовані тести погодженого обсягу проходять у CI, немає відкритих критичних дефектів цього обсягу; сукупне покриття рядків і гілок API ≥80% — ціль стратегії після додавання інтеграційних тестів, критичних модулів зі стратегії ≥95%; базовий CI-поріг — 70%.

**Ризики:** найвищий пріоритет — несанкціонована зміна даних ментором або доступ після відкликання; далі — втрата порядку карток через однакові індекси й незбереження змін у PostgreSQL; потім — невалідні дані та повільне оновлення інтерфейсу. З цих ризиків починається таблиця.

Локальний запуск у PowerShell після встановлення залежностей:

```powershell
docker run --detach --name monkey-lab07-postgres --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_DB=monkey_lab07 --publish 127.0.0.1:55432:5432 postgres:16
$env:TEST_DATABASE_URL = 'postgresql+psycopg://postgres@127.0.0.1:55432/monkey_lab07'
python -m pytest tests/test_card_order.py tests/test_card_order_postgres.py --no-cov -v
python -m pytest
docker stop monkey-lab07-postgres
```

Дочекайтеся готовності PostgreSQL перед pytest. Якщо контейнер уже створено, використайте `docker start monkey-lab07-postgres`. З'єднання без пароля призначене лише для ізольованої локальної тестової БД, опублікованої на loopback. TP-04 створює власну схему `lab07_<uuid>` і видаляє лише її після перевірки. Продукційна залежність `get_repositories` відкриває та фіксує окрему транзакцію кожного запиту; перевірка БД виконується новою сесією. Без `TEST_DATABASE_URL` цей тест явно пропускається; CI job `Lab07 card ordering / postgres-card-order` завжди задає PostgreSQL.

### Уточнення TP-12 після відгуку

Власник має зафіксувати три моменти: `t0` — натискання «Додати» після заповнення поля, `t1` — успішна відповідь API, `t2` — посилання видиме в UI. У протоколі окремо навести час HTTP-операції `t1−t0`, оновлення UI `t2−t1` і загальний `t2−t0`. Поріг PERF-4 застосовується до загального часу: **кожне з 30 вимірювань ≤300 мс**. Повторний GET підтверджує збереження. Зазначити середовище, команду, усі 30 результатів і максимум. Наявний Playwright-тест починає відлік перед заповненням поля та не має окремого GET після додавання — його результат ще не підтверджує цей уточнений протокол.
