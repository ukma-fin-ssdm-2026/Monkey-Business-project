## 1. Поточний статус тестування
На поточному етапі в проєкті розгорнуто автоматизований набір модульних тестів на базі фреймворку **pytest**.
- **Структура тестів:**
  - `tests/test_auth.py`: Автентифікація, випуск та перевірка JWT-токенів, PBKDF2-хешування паролів, матриця ролей, зміна паролів (62 тести).
  - `tests/test_stages.py`: Керування Канбан-етапами дошки (FR-003, FR-024), сортування, права доступу, валідація цілісності (16 тестів).
  - `tests/test_mentors.py`: Запрошення менторів, валідація токенів, перевірка read-only обмежень (3 тести).
  - `tests/test_validators.py`: Бізнес-валідація посилань на вакансії та захист від SSRF (6 тестів).
  - `tests/test_properties.py`: Property-based тести на базі Hypothesis (2 тести).
- **Загальна кількість модульних тестів:** 89 тестів (100% успішне проходження).
- **Ізоляція:** Тести використовують in-memory тестові дублери (`InMemoryRepository`), фікстури pytest та моки (`unittest.mock.Mock`), що забезпечує виконання всього набору за <25 секунд без потреби у запущеній СУБД.

## 3. Плани подальшого розвитку рівнів тестування (Testing Pyramid)

1. **Інтеграційні тести (Integration Testing):**
   - Тестування кінцевих точок API через `httpx.AsyncClient` / `TestClient` з тестовою базою даних PostgreSQL у Docker Compose.
   - Перевірка виконання Alembic-міграцій (upgrade / downgrade) та збереження консистентності зовнішніх ключів.
2. **Системні та приймальні тести (E2E / Acceptance):**
   - Автоматизація користувацьких сценаріїв (US-001 – US-008) через Playwright / Cypress для перевірки drag-and-drop переміщення карток на Канбан-дошці.
   - Тестування взаємодії кандидата та ментора в режимі реального часу.
3. **Нефункціональне тестування:**
   - **Продуктивність (Performance):** Навантажувальне тестування ключових ендпоінтів через Locust / k6 для підтвердження NFR (PERF-1: завантаження дошки $\le 1$ с при 100 картках; PERF-2: відповідь API $\le 200$ мс для 95% запитів).
   - **Безпека (Security):** Автоматизоване сканування на вразливості через OWASP ZAP, Bandit (SAST) та перевірка ролей BOLA/IDOR.

## 4. Інтеграція в конвеєр CI/CD
Тестування повністю інтегровано в GitHub Actions ([.github/workflows/ci.yml](../../.github/workflows/ci.yml)):
1. **Тригери:** Запуск на кожен `push` та `pull_request` у гілку `main`.
2. **Кроки пайплайну:**
   - Встановлення залежностей проєкту та середовища тестування.
   - Запуск `pytest` з генерацією звітів у форматах terminal, HTML та XML (`coverage.xml`).
   - Перевірка порогу якості покриття (`--cov-fail-under=70`). Якщо показник нижчий — пайплайн падає з помилкою.
   - Автоматичне додавання резюме покриття до GitHub Actions Job Summary.
   - Збереження звітів `htmlcov` як артефактів білду.

## 5. Обсяг тестування, метрики та ворота якості

### 5.1 Обсяг тестування
- **Модульний рівень:** `auth.py`, `domain.py`, `validators.py`, `routers/stages.py`, `routers/mentors.py`, `repositories/sql.py`, `errors.py`, `db.py`. Тут бізнес-правила й безпека (JWT, хешування паролів, блокування після невдалих входів, матриця ролей, SSRF-валідація): помилка ламає доступ або дані, а ізолювати цей код дешево.
- **Інтеграційний рівень (Лаб. 7):** виключені роутери з розділу 2, а також непокриті частини `routers/mentors.py` (прийняття й відкликання запрошень), `repositories/sql.py`, `db.py` і `errors.py` (обробники помилок FastAPI). Їхня поведінка залежить від PostgreSQL і HTTP-конвеєра, тож моки перевіряли б самі себе.
- **Відома прогалина:** `validate_vacancy_url` пропускає `http://[::1]/` і приватні мережі (`http://10.0.0.5/`); потрібні тест і виправлення в межах перевірок безпеки з розділу 3.

### 5.3 Ворота якості (політика злиття в `main`)
Доповнює Definition of Done зі [Статуту, розділ 5](../../TeamCharter.md#5-політика-якості-та-огляду-коду). PR зливається, лише якщо:
1. `CI / build` зелений: усі тести проходять, покриття рядків ≥ 70% (`--cov-fail-under=70`), специфікація OpenAPI без дрейфу.
2. `Static analysis` зелений: black, flake8, bandit, detect-secrets.
3. Нова або змінена логіка в `src/api` має тести, а покриття критичного модуля не опускається нижче 95% (ревʼюер звіряє Job Summary з `main`).
4. Виправлення бага містить регресійний тест у тому самому PR.
5. Тест не вимикають (`@pytest.mark.skip`) без issue з причиною; нестабільний тест виправляють, а не перезапускають.
6. Є щонайменше одне схвалення рев'ю.

### 5.4 Вибір інструментів

| Інструмент | Для чого | Чому саме він |
|---|---|---|
| pytest (фікстури, `parametrize`) | модульні тести | стандарт для Python і FastAPI, мінімум шаблонного коду |
| pytest-cov (coverage.py) | покриття рядків і гілок, HTML/XML, `--cov-fail-under` | один інструмент і для звіту, і для воріт у CI |
| `unittest.mock`, `InMemoryRepository` | тестові дублери | ізоляція від PostgreSQL і пошти, швидкі детерміновані тести |
| Hypothesis | property-based тести | сам підбирає граничні входи (Unicode, порожні рядки, емодзі) |
| mutmut 2.5.1 | мутаційне тестування | перевіряє силу асертів, а не лише виконання рядків; mutmut 3.x не підтримує імпорти `src.*` |
| black, flake8, bandit, detect-secrets | статичний аналіз | див. Статут, розділ 5 |

# Бонуси

### Бонус №1: Тести на основі властивостей (Property-Based Testing)
У тестовий набір додано модуль `tests/test_properties.py` з використанням бібліотеки **Hypothesis**:
- **Властивість 1 (Round-trip інваріантність хешування паролів):**
  - *Формулювання:* «Для будь-якого випадково згенерованого текстового пароля $s$ функція верифікації `_verify_password(s, _hash_password(s))` завжди повертає `True` для оригінального пароля і `False` для будь-якої його модифікації».
  - *Чому має виконуватися:* Це фундаментальний криптографічний інваріант безпеки автентифікації: хеш повинен однозначно верифікуватися лише оригінальним входом незалежно від набору символів (включаючи пробіли, емодзі, Unicode).
- **Властивість 2 (Монотонність сортування етапів):**
  - *Формулювання:* «Для будь-якої випадкової перестановки цілочисельних індексів `order_index`, відсортований список гарантує, що для кожного елемента $i$ виконується $order\_index_i \le order\_index_{i+1}$».

### Бонус №3: Мутаційне тестування (Mutation Testing)
- **Модуль:** `src/api/validators.py`; налаштування — `[tool.mutmut]` у [pyproject.toml](../../pyproject.toml).
- **Запуск:** `pip install -r requirements-dev.txt`, далі з активованим `.venv`: `mutmut run`, `mutmut results`, `mutmut show <id>`.
- **Оцінка мутацій:** до — 20 мутантів, 17 вбито, 3 вижили → **85%**; після трьох дописаних тестів — 20 з 20 → **100%**.
- **Мутант, що вижив (#9):** жоден тест не подавав URL без хоста, тому з цим мутантом `https://` вважався коректним посиланням.

```diff
 def _is_safe_host(hostname: str | None) -> bool:
     if not hostname:
-        return False
+        return True
```

- **Тест, що його вбиває** (`tests/test_validators.py`):

```python
def test_validate_vacancy_url_rejects_url_without_host():
    assert validate_vacancy_url("https://") is False
    assert validate_vacancy_url("http:///path/only") is False
```

- **Інші два мутанти:** #14 замінював `or` на `and` у перевірці типу й вижив, бо тест `rejects_empty_and_non_string` насправді не передавав не-рядок; його вбиває `test_validate_vacancy_url_rejects_truthy_non_string`. #20 повертав `True` з гілки `except`, яку жоден тест не досягав; його вбиває `test_validate_vacancy_url_rejects_unparseable_url` з `http://[::1`.
