# Стратегія тестування — Лаб06

**Проєкт:** Monkey-Business-project. Основна частина — одна сторінка; бонуси наведено окремо.

## Поточний стан

**137 сценаріїв pytest проходять, без skip/xfail:** 119 сценаріїв вихідного набору, 5 доданих регресій і 13 тестів валідатора URL (TDD-відхилення внутрішніх адрес і мутаційне тестування). Обсяг модульної частини лабораторної вже забезпечують `stages.py` та `validators.py`: разом 37 сценаріїв, фікстури, in-memory дублери, Mock, параметризація, права доступу та граничні випадки. Наявні тести auth і mentors збережено. Нові регресії обмежені двома знайденими дефектами: відсутній ментор і невідповідність User ↔ ORM. Структура AAA, репозиторії й пошта ізольовані від зовнішніх сервісів; PostgreSQL для прогону не потрібний.

## Покриття та прогалини

Запуск: `python -m pytest`. Звіти: [`htmlcov/index.html`](../../htmlcov/index.html) і [`coverage.xml`](../../coverage.xml).

**Загальне покриття з гілками — 72,55%**; рядки — **73,89% (818/1107)**, гілки — **63,69% (107/168)**. Джерело — весь `src/api`, включно зі схемами, SQL та HTTP/MCP-адаптерами; виключено лише порожні `__init__.py`. `auth.py`, `stages.py`, `validators.py` мають 100% рядків і гілок, `mentors.py` — 98,05% за спільною метрикою.

У вибраний обсяг модульного тестування не входять операції `card_links`, `card_notes`, `comments` (0%) та більша частина `cards` (55%); їх не приховано зі звіту. Непокриті також запуск HTTP/MCP, частина SQL-запитів, транзакцій та HTTP-обробників помилок. Модульні тести зі сховищами-дублерами цих взаємодій не перевіряють. Високий відсоток декларацій ORM/схем сам по собі не доводить коректність поведінки. 100% не є самоціллю: важливі права доступу, заборонені операції та граничні випадки.

## План розвитку тестування

Це передбачений умовою план; обов'язкові модульні тести, аналіз покриття й звіти виконано в Лаб06.

- **Інтеграційні:** API + PostgreSQL, міграції, foreign keys, commit/rollback, ізоляція дошок і HTTP-формат помилок.
- **Системні:** реєстрація → дошка → створення/переміщення картки → запрошення ментора.
- **Приймальні:** звірка сценаріїв кандидата й ментора з критеріями користувацьких історій; ментор може коментувати, але не змінювати дані кандидата.
- **Продуктивність/безпека:** замір p95 за NFR; перевірки JWT, доступу до чужих ресурсів, приховування секретів у помилках. Модульні перевірки ролей уже є; навантажувальний прогін не заявляється.

## CI/CD

Наявний [workflow](../../.github/workflows/ci.yml) запускає тести на push у `main` та PR до `main`, генерує HTML/XML, додає підсумок і публікує артефакт. Поріг **70%** застосовується до всього API з гілками; він дає базовий захист від істотної втрати покриття, а критичні права доступу перевіряються окремими негативними тестами. Локальний результат проходить поріг; віддалений успішний GitHub Actions run потрібно підтвердити після коміту.

**Ворота злиття в `main`** (доповнюють Definition of Done зі [Статуту, розділ 5](../../TeamCharter.md#5-політика-якості-та-огляду-коду)): зелені `CI / build` (тести, покриття ≥ 70%, OpenAPI без дрейфу) і `Static analysis` (black, flake8, bandit, detect-secrets); нова логіка має тести, а критичний модуль не опускається нижче 95%; виправлення бага містить регресійний тест; `skip` лише з issue, нестабільний тест виправляють, а не перезапускають; щонайменше одне схвалення рев'ю.

**Інструменти:** pytest і pytest-cov — стандарт для FastAPI, один інструмент і для звіту, і для воріт; `unittest.mock` та in-memory репозиторії — ізоляція від PostgreSQL і пошти; Hypothesis — граничні входи, про які не подумали; mutmut 2.5.1 — перевіряє силу асертів (3.x не підтримує імпорти `src.*`).

**Рекомендації для керівника інтеграції:** окрема job з інтеграційними тестами та сервіс-контейнером PostgreSQL; `mutmut` запускати вручну (`workflow_dispatch`) або щотижня, а не на кожен PR.

# Бонуси

- **Property-based:** [`tests/test_properties.py`](../../tests/test_properties.py), Hypothesis. Оригінальний згенерований пароль проходить перевірку свого хешу, пароль із доданим `!` — ні; публічний HTTP(S) URL приймається також із зовнішніми пробілами. Це очікувані інваріанти перевірки паролів та очищення URL. Перевірка URL викликає код проєкту; задано `derandomize=True`.
- **Ворота покриття:** 70% у конфігурації та CI, локально 72,55%. Для підтвердження бонусу додайте посилання на успішний GitHub Actions run. Локальний прогін не підтверджує віддалений CI.

- **Мутаційне тестування:** mutmut 2.5.1 по `src/api/validators.py` (налаштування `[tool.mutmut]` у [`pyproject.toml`](../../pyproject.toml), запуск `mutmut run`). Перший прогін: 17 з 20 мутантів вбито (85%). Мутант, що вижив: `if not hostname: return False` → `return True`, бо жоден тест не подавав URL без хоста; його вбиває `test_validate_vacancy_url_rejects_url_without_host` (`https://`, `http:///path/only`). Разом із двома іншими дописаними тестами — 20/20 (100%). Після TDD-змін валідатора — 22/23 (96%): єдиний живий мутант еквівалентний, бо `rstrip("XX.XX")` після `.lower()` діє так само, як `rstrip(".")`.

Кожен заявлений бонус має пояснити у відео хоча б один учасник. Ручний debugging challenge не є виконаним бонусом мутаційного тестування.
