## Як запустити

```bash
pip install -r requirements-dev.txt

black --check src          # форматування (без змін файлів)
flake8 src                 # стиль
bandit -c pyproject.toml -r src   # аналізатор безпеки
pre-commit run --all-files # усе разом + пошук секретів
```

Щоб хуки спрацьовували автоматично перед кожним комітом, один раз виконайте `pre-commit install`. Ці самі перевірки запускаються в CI (`.github/workflows/static-analysis.yml`) для кожного Pull Request і push у `main`.

### Аналізатор безпеки: bandit не знайшов вразливостей у коді API

Bandit не повідомив знахідок у `src/` у повторному прогоні 31.10.2026 на `85f131b` (2544 рядки коду; детальні метрики — вище). Це не доказ відсутності вразливостей: аналізатор не перевіряє повноту бізнес-правил доступу чи поведінку транзакцій. Нижче збережено попередній демонстраційний експеримент з аналізатором, актуалізовано розбір загрози та описано виправлений витік, який Bandit не виявляв. Демонстраційний експеримент і всі хуки pre-commit у цьому оновленні повторно не запускалися.

**1. Перевірка, що аналізатор взагалі здатен щось знайти.** У тимчасовий файл (у репозиторій не потрапив) додано навмисно вразливий код:

```python
AWS_SECRET_ACCESS_KEY = "AKIA_FAKE_KEY_FOR_DEMO_PURPOSES_ONLY_98765" # pragma: allowlist secret 
# (проігноровано тільки для звіту)

def find_user(cursor, email):
    query = "SELECT * FROM users WHERE email = '%s'" % email
    cursor.execute(query)
```

Bandit із тією самою конфігурацією повідомив:

| ID правила | Серйозність / впевненість | CWE | Що знайдено |
|---|---|---|---|
| `B608` (`hardcoded_sql_expressions`) | Medium / Low | CWE-89 | SQL-запит збирається форматуванням рядка — вектор SQL-ін'єкції |
| `B105` (`hardcoded_password_string`) | Low / Medium | CWE-259 | захардкоджений пароль/ключ у рядку |



**2. Загроза з threat-model.md: R7 — Elevation of privilege (підвищення привілеїв) через помилку в реалізації RBAC-перевірки (SEC-3).** Ризик: помилка в реалізації перевірки прав доступу (RBAC) — наприклад, пропущена захисна залежність Depends(require_role(...)) на новому ендпоінті — може дозволити ментору або неавторизованому користувачу виконати мутуючу операцію (редагування чи видалення карток кандидатів), хоча вимоги безпеки (SEC-3) це прямо забороняють.

Як цьому протистоїть поточний код і процес:

- Мутуючі кінцеві точки карток, етапів, посилань і нотаток використовують `CandidateOrAdmin` (`auth.py`, `require_roles(UserRole.candidate, UserRole.admin)`), тож ментор отримує `403` до виконання обробника. Запрошення та відкликання доступу в [`routers/mentors.py`](../../src/api/routers/mentors.py) також вимагають `CandidateOrAdmin` і перевірки конкретної дошки. Коментарі — окремий дозволений сценарій: [`routers/comments.py`](../../src/api/routers/comments.py) використовує `CurrentUser`, перевіряє доступ до дошки й належність картки; видалення дозволене автору або адміністратору.
- Доступ до конкретної дошки перевіряє `require_board_access(..., write=True)` за принципом deny-by-default: дозвіл мають лише адміністратор, кандидат-власник дошки і, тільки для читання, ментор із прийнятим запрошенням; в усіх інших випадках — `403`.
- Історична ручна перевірка на `ee1b121` використовувала запрошення, додане безпосередньо в БД: ментор отримував `200` на читання карток і `403` на зміну картки та створення нотатки. У поточному коді вже є ендпоінти запрошень; сценарії прийняття й відкликання перевіряють [`tests/test_mentors.py`](../../tests/test_mentors.py) та [`tests/integration/test_mentor_access_integration.py`](../../tests/integration/test_mentor_access_integration.py). Ці тести в межах оновлення звіту не запускалися.
- Огляд коду перед злиттям PR перевіряє захист кожної нової мутуючої кінцевої точки (критерій «безпека» в розділі 5 `TeamCharter.md`).

**Обмеження.** Залежність оголошено в кожній кінцевій точці окремо, а не на рівні роутера (`APIRouter(dependencies=[...])`), тому новий захищений ендпоінт без залежності перевірки користувача може залишитися відкритим. Публічні маршрути входу, реєстрації та перевірки запрошення за токеном слід оцінювати за їхнім окремим контрактом. У Лаб06 додано модульні тести матриці ролей (`tests/test_auth.py`) та негативні перевірки запису ментора в роутерах; повнота захисту HTTP-маршрутів додатково потребує огляду коду.

**Чесне обмеження.** Інструменти статичного аналізу коду (такі як bandit чи лінтери) сканують код на наявність небезпечних синтаксичних конструкцій і патернів, проте вони не можуть автоматично зрозуміти бізнес-логіку прав доступу. Тому захист від таких логічних вразливостей забезпечується комбінацією архітектурних патернів FastAPI (Depends), суворим Code Review, модульними тестами ролей у `tests/` та планом перевірки HTTP-маршрутів у `docs/testing/testing-strategy.md`.

**3. Вразливість, яку bandit не виявив: розкриття тіла запиту у відповіді 422 (CWE-209).**

- **Що знайдено:** коли в тілі запиту бракує обов'язкового поля, обробник помилок валідації (`errors.py`, `handle_validation_error`) повертає в `details[].provided_value` значення `err["input"]`, а для помилки типу `missing` Pydantic кладе туди все тіло запиту. Запит `POST /v1/auth/login` з тілом `{"password": "..."}` отримує пароль у відповіді `422`.
- **Чим знайдено:** оглядом нашого коду командою SSDM_12 ([їхній звіт](https://github.com/ukma-fin-ssdm-2026/SSDM_12/blob/4d670a592e625398d0a4bd05f3af461c6a04d5a8/docs/code-quality/review-report.md)); відтворено запитом до API. Правила bandit такий логічний витік не охоплюють.
- **Чому це ризик:** пароль та інші чутливі поля потрапляють у тіло відповіді, а тіла відповідей 4xx — у логи проксі та моніторингу; це підсилює ризик R1 з `threat-model.md`. Компроміс щодо `provided_value` уже зазначено в `docs/api/quality-attributes.md` (розділ «Аналіз компромісів»).
- **Статус:** виправлено. `errors.py` (`_safe_provided_value`) не повертає `input` для помилок типу `missing`, для словників і списків та для полів із `password`, `token`, `secret` у назві, а решту значень обрізає до 100 символів. Регресійні тести — [`tests/test_errors.py`](../../tests/test_errors.py); вони падали на коді до виправлення.

## Аудит залежностей (Бонус 2)

Для постійного моніторингу безпеки сторонніх бібліотек налаштовано **Dependabot** (`.github/dependabot.yml`): щотижня він перевіряє залежності pip (`requirements.txt`, `requirements-dev.txt`) і GitHub Actions, створює Pull Request з оновленнями та сповіщення про залежності з відомими вразливостями (CVE).

**Знахідка:** сповіщення Dependabot #1 від 2026-10-11 — [GHSA-3936-cmfr-pm3m](https://github.com/advisories/GHSA-3936-cmfr-pm3m) (CVE-2026-32274), серйозність **High**.

| Поле | Значення |
|---|---|
| Пакет | `black` 24.10.0 на момент сповіщення (`requirements-dev.txt` і ревізія хука в `.pre-commit-config.yaml`) |
| Вразливі версії | `>= 24.3.0, < 26.3.1`; виправлено в 26.3.1 |
| Суть | black формує ім'я файлу кешу з опцій форматування, і значення опції `--python-cell-magics` потрапляє в нього без санітизації, тож той, хто контролює цю опцію, може записати файл кешу в довільне місце файлової системи |

**Оцінка для нашого проєкту:** black — інструмент розробки: його немає в `requirements.txt` і в Docker-образі API. Він запускається лише на нашому коді — у хуку pre-commit без додаткових аргументів і в CI як `black --check src`; опцію `--python-cell-magics` ми не використовуємо, а в `pyproject.toml` для black задано лише `line-length` і `target-version`. Щоб скористатися вразливістю, потрібен контроль над аргументами black, тобто право змінювати конфігурацію репозиторію, яке й так дозволяє виконати будь-який код у CI.

**Рішення: виправлено.** black оновлено до 26.10.1 одночасно в `requirements-dev.txt` і в ревізії хука `.pre-commit-config.yaml`, як вимагає розділ 5 `TeamCharter.md`. Pull Request від Dependabot (#116 і #117) не проходили `black --check`, бо змінювали лише `requirements-dev.txt`, а нова версія переформатовує код; тому оновлення зроблено окремим комітом разом із переформатуванням — нова версія прибрала по одному порожньому рядку в `src/api/schemas.py` і `migrations/versions/0001_initial_schema.py`. Після оновлення black, flake8, bandit і detect-secrets проходять без зауважень, а специфікація OpenAPI не змінилася. Після злиття в `main` сповіщення #1 закриється автоматично, а Pull Request #116 і #117 стануть непотрібними.
