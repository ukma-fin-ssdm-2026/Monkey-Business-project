# Звіт про прогрес розробки та структуру коду (Progress Report)

## 1. Загальний огляд

У межах **Лабораторної роботи 5: Конструювання I – Якість коду, стандарти та огляд** команда реалізувала та розширила початковий робочий каркас бекенду для системи **Tech Interview Board**, а також розробила повноцінний клієнтський додаток на React + TypeScript (Vite). 

Бекенд побудовано на базі фреймворку **FastAPI (Python 3.12)** із монолітною клієнт-серверною архітектурою згідно з [ADR-002](../architecture/decisions/ADR-002.md) та моделлю даних [data-model.md](../architecture/data-model.md). Дані зберігаються в **PostgreSQL**, а бекенд і база даних запускаються в Docker Compose відповідно до [діаграми розгортання](../architecture/uml/deployment-diagram.png).

Фронтенд реалізовано як сучасний односторінковий додаток (SPA) на React + TypeScript, який взаємодіє з бекенд-API, забезпечуючи повноцінний користувацький інтерфейс для кандидатів і менторів.

Код організовано за модульним принципом, дотримуючись суворих стандартів якості:
- Повна відповідність стандарту **PEP 8** та форматування інструментом **Black** (довжина рядка 88).
- Чистий лінтинг через **Flake8** без зауважень.
- Перевірка безпеки аналізатором **Bandit** (0 знахідок).
- Перевірка секретів **detect-secrets** та аудит залежностей **Dependabot**.
- Автоматична генерація та синхронізація специфікації OpenAPI (`docs/api/openapi-generated.yaml`) без дрифту в CI.

Правила якості закріплено в [TeamCharter.md](../../TeamCharter.md), розділ 5 «Політика якості та огляду коду».

## 2. Структура кодової бази проєкту

Код бекенду розміщено в каталозі `src/api/` , а фронтенду — у `src/frontend/src/`:

```
src/
├── api/                    # Бекенд (FastAPI)
│   ├── main.py             # Точка входу FastAPI додатку, підключення роутерів, автогенерація OpenAPI
│   ├── schemas.py          # Моделі Pydantic v2 для вхідної/вихідної валідації та схем помилок
│   ├── domain.py           # Доменні сутності (dataclass) без залежності від бази даних
│   ├── db.py               # Підключення до БД і транзакція на запит (залежність FastAPI Repos)
│   ├── auth.py             # Автентифікація (JWT Bearer), хешування паролів, RBAC (Depends)
│   ├── errors.py           # Централізована обробка винятків та єдиний формат ErrorResponse
│   ├── mcp_server.py       # MCP-сервер з API (FastMCP) для AI-агентів
│   ├── repositories/
│   │   ├── base.py         # Інтерфейси репозиторіїв — шар між API та СУБД
│   │   └── sql.py          # Реалізація для PostgreSQL на SQLAlchemy 2.0: таблиці та запити
│   └── routers/
│       ├── stages.py       # Керування етапами Канбан-дошки (FR-003)
│       ├── cards.py        # Картки вакансій, фільтрація, переміщення drag-and-drop (FR-004–FR-010)
│       ├── card_links.py   # Посилання на тестові завдання для картки (FR-009)
│       └── card_notes.py   # Нотатки та фідбек до картки вакансії (FR-011, FR-022)
└── frontend/
    └── src/
        ├── api/          # Типи (1:1 зі schemas.py) і fetch-клієнт з обробкою ErrorResponse
        ├── context/      # AuthContext (токен, користувач, обраний board_id)
        ├── components/   # StageColumn, CardItem, CardModal, NewCardForm, ProtectedRoute
        ├── pages/        # LoginPage, RegisterPage, BoardSetupPage, BoardPage
        ├── App.tsx       # Головний компонент додатку та маршрутизація
        └── main.tsx      # Точка входу React
migrations/               # Міграції схеми БД (Alembic), 0001 — початкова схема
Dockerfile                # Образ Backend API
docker-compose.yml        # Контейнери Backend API та PostgreSQL
```

## 3. Реалізовані компоненти та ендпоінти

У цій лабораторній роботі Керівник якості (Nikita Dyshlyuk) у взаємодії з командою розширив доменну модель бекенду, реалізувавши ключові ендпоінти для повноцінної роботи Канбан-дошки. Перехід на PostgreSQL із шаром репозиторіїв ([#118](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/118)) та автентифікацію MCP-сервера ([#120](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/120)) реалізував Nazar Sydorchuk.

### 3.1. Канбан-етапи (`routers/stages.py`)
Забезпечує конфігурацію стовпчиків Канбан-дошки відповідно до **FR-003** (стандартні етапи: «Відгук», «Скринінг», «Технічне інтерв'ю», «Офер»). Етапи налаштовуються для окремої дошки; зміна адміністратором стандартного набору етапів для нових дошок (**FR-024**) ще не реалізована:
- `GET /v1/boards/{board_id}/stages`: Отримання всіх етапів дошки у відсортованому порядку (`order_index`).
- `POST /v1/boards/{board_id}/stages`: Додавання нового кастомного етапу на дошку (доступ лише власнику або адміну).
- `PATCH /v1/boards/{board_id}/stages/{stage_id}`: Зміна назви або порядку сортування етапу.
- `DELETE /v1/boards/{board_id}/stages/{stage_id}`: Видалення етапу з контролем цілісності даних (якщо на етапі є картки — повертається `409 Conflict`).

### 3.2. Нотатки та фідбек (`routers/card_notes.py`)
Покриває вимогу **FR-011** щодо збереження нотаток і зворотного зв'язку від рекрутерів, а також закладає основу для збереження результатів AI-асистента (**FR-022**):
- `GET /v1/boards/{board_id}/cards/{card_id}/notes`: Отримання списку нотаток картки в хронологічному порядку створення.
- `POST /v1/boards/{board_id}/cards/{card_id}/notes`: Створення нової нотатки з вказанням автора/джерела (`candidate`, `recruiter`, `ai`).
- `PATCH /v1/boards/{board_id}/cards/{card_id}/notes/{note_id}`: Редагування тексту нотатки.
- `DELETE /v1/boards/{board_id}/cards/{card_id}/notes/{note_id}`: Видалення нотатки.

### 3.3. Картки вакансій (`routers/cards.py`)
Реалізовано повний життєвий цикл карток вакансій:
- `GET /v1/boards/{board_id}/cards`: Список карток із фільтрацією за етапом (`stage_id`), статусом (`status`) та оффсет-пагінацією.
- `POST /v1/boards/{board_id}/cards`: Створення картки з обов'язковою валідацією полів `company`, `position` та `stage_id` (FR-007); етап має належати цій дошці, інакше — `404`.
- `GET /v1/boards/{board_id}/cards/{card_id}`: Отримання детальної інформації про картку.
- `PATCH /v1/boards/{board_id}/cards/{card_id}`: Часткове оновлення полів картки або її закриття (FR-006, FR-008).
- `DELETE /v1/boards/{board_id}/cards/{card_id}`: Видалення картки разом з її посиланнями та нотатками.
- `POST /v1/boards/{board_id}/cards/{card_id}/move`: Переміщення між етапами та зміна порядку (FR-004, FR-005).

### 3.4. Посилання на тестові завдання (`routers/card_links.py`)
- `GET /v1/boards/{board_id}/cards/{card_id}/links`: Список посилань картки (FR-009).
- `POST /v1/boards/{board_id}/cards/{card_id}/links`: Додавання нового посилання з суворою перевіркою URL (`HttpUrl`).
- `DELETE /v1/boards/{board_id}/cards/{card_id}/links/{link_id}`: Видалення посилання.

### 3.5. Автентифікація та авторизація (`auth.py`)
- `POST /v1/auth/register`: Реєстрація кандидата (FR-001, FR-002, SEC-1); разом з обліковим записом створюється його дошка з чотирма стандартними етапами.
- `POST /v1/auth/login`: Авторизація та отримання JWT Bearer токена на 24 години (SEC-2).
- Механізм `Depends(require_roles)` та `require_board_access`: Забезпечення RBAC, захист карток від редагування/видалення ментором (SEC-3, FR-014).

### 3.6. Зберігання даних: PostgreSQL і шар репозиторіїв ([#118](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/118))
- Роутери та `auth.py` працюють лише з інтерфейсами репозиторіїв (`repositories/base.py`) і доменними сутностями (`domain.py`) та не імпортують SQLAlchemy. Реалізація для PostgreSQL — `repositories/sql.py`; щоб змінити СУБД, достатньо нової реалізації інтерфейсів і заміни однієї функції в `db.py`.
- Схема з 7 таблиць за [data-model.md](../architecture/data-model.md): `users`, `boards`, `stages`, `cards`, `card_links`, `card_notes`, `board_mentors`. Зовнішні ключі каскадно видаляють посилання й нотатки разом із карткою та не дають видалити етап, у якому є картки; email користувача унікальний; картки дошки вибираються за індексом (PERF-1).
- Схема змінюється лише міграціями Alembic (`migrations/versions/0001_initial_schema.py`).
- Кожен запит виконується в одній транзакції: зміни фіксуються до відправлення відповіді, а при помилці відкочуються.
- Демонстраційні дані з in-memory заглушки прибрано: обліковий запис і дошку створює `POST /v1/auth/register`.

### 3.7. Розгортання в Docker Compose
- `docker compose up -d --build` запускає контейнери **Backend API** (FastAPI + Uvicorn; застосовує міграції при старті) та **PostgreSQL 17** (дані в томі `pgdata`) в одній мережі `backend`, як на діаграмі розгортання.
- Обидва контейнери мають перевірку стану (healthcheck) та автоматичний перезапуск (`restart: always`, REL-1); порти опубліковано лише на `127.0.0.1`.
- Інструкції запуску — у [`src/api/README.md`](../../src/api/README.md).

### 3.8. MCP-сервер ([#120](https://github.com/ukma-fin-ssdm-2026/Monkey-Business-project/pull/120))
- `mcp_server.py` перетворює всі кінцеві точки, крім `/v1/auth/*`, на 18 інструментів для AI-агентів (Claude Code, Claude Desktop, Cursor).
- Сервер входить через `/v1/auth/login` від імені облікового запису з `MCP_USER_EMAIL` / `MCP_USER_PASSWORD` і додає Bearer-токен до кожного запиту, тож агент має права цього користувача і перевірки RBAC не обходяться.

### 3.8. Фронтенд-частина (`src/frontend`)
Клієнтський додаток на **React + TypeScript** зв'язує всі компоненти API в єдиний інтерфейс.

### Особливості інтеграції з API

Оскільки специфікація бекенду поки не має окремого ендпоінта для отримання списку дошок поточного користувача («мої дошки»), фронтенд вирішує це на своєму рівні: після входу користувач вводить свій `board_id` на сторінці `/board/setup`, який зберігається в `localStorage` для поточної сесії. 

Кандидат може отримати свій `board_id` через команду в базі даних:

```bash
docker compose exec db psql -U interview_board -d interview_board \
  -c "select b.id from boards b join users u on u.id = b.owner_id where u.email = 'you@example.com'"
```

### Реалізований функціонал фронтенду:
- **Автентифікація:** Реєстрація та вхід у систему з використанням JWT Bearer та збереженням токена в `localStorage`.
- **Канбан-дошка:** Відображення етапів-колонок, підтримка повноцінного drag-and-drop карток між етапами та в межах одного етапу (`@hello-pangea/dnd`), виклик `POST .../cards/{id}/move`.
- **Управління етапами:** Створення, перейменування та видалення етапів (з обробкою помилки `409 Conflict`, якщо в етапі є картки).
- **Робота з картками:** Повний CRUD для карток (компанія, посада, URL вакансії, вимоги, дедлайн, нагадування, статус).
- **Тестові завдання та нотатки:** Додавання та видалення посилань на тестові завдання й нотаток/фідбеку до карток.
- **Рольові обмеження в UI:** Роль `mentor` бачить дошку виключно в режимі перегляду (без drag-and-drop, форм створення чи редагування), що відповідає обмеженням бекенду (`require_board_access`, `CandidateOrAdmin`).
- **Централізована обробка помилок:** Відображення повідомлень про помилки API через стандартний формат `ErrorResponse.error.message`.

## 4. Відповідність стандартам якості та безпеки

1. **Єдиний формат обробки помилок:** Усі ендпоінти використовують стандартизований клас `ErrorResponse`, що повертає машинний код (`NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `FORBIDDEN`), зрозуміле повідомлення, ідентифікатор `request_id` та посилання на документацію API.
2. **Типізація та валідація:** Усі параметри маршрутів, query-параметри та тіла запитів строго типізовані за допомогою Pydantic v2 та анотацій FastAPI.
3. **Захист від невалідних даних:** Реалізовано перевірки на непорожні рядки (`not_blank`), обмеження довжини полів, валідацію UUID та коректність HTTP/HTTPS посилань.
4. **Контроль безпеки:** Захист паролів алгоритмом `PBKDF2-HMAC-SHA256` із сіллю; запити до БД будуються лише параметризовано через SQLAlchemy ORM, без конкатенації рядків (ризик R3 у [threat-model.md](../architecture/threat-model.md)); викликів `eval`/`subprocess` немає.
5. **Статичний аналіз поточного коду** (коміт `ee1b121`): bandit — 0 знахідок на 1749 рядках коду в 13 модулях `src/api/`, 0 позначок `# nosec`; flake8 — 0 зауважень; black — без змін.

## 6. Відомі обмеження та наступні кроки

- **Потенційна вразливість (CWE-209):** коли в запиті бракує обов'язкового поля, відповідь `422` повертає в `provided_value` усе тіло запиту — зокрема пароль у `POST /v1/auth/login`. Знайдено під час огляду нашого коду командою SSDM_12; потрібне виправлення в `errors.py` з регресійним тестом.
- `PATCH` картки не може очистити необов'язкове поле (`vacancy_url`, `requirements_text`, `deadline`): явний `null` ігнорується.
- `move` не перераховує позиції інших карток етапу.
- Немає кінцевої точки, що повертає дошку поточного користувача, тому `board_id` після реєстрації доводиться брати з БД.
- Ще не реалізовано: запрошення ментора, коментарі та відкликання доступу (FR-012, FR-013, FR-015), нагадування про дедлайни (FR-016–FR-018; поле `notifications_enabled` уже зберігається), аналітика (FR-019–FR-021), AI-асистент (FR-022; джерело нотатки `ai` уже є), адміністрування та підтримка (FR-023–FR-026).

## 7. Готовність до Лабораторної роботи 6

Поточна кодова база становить **мінімальний робочий прототип (MVP)**:
- Бекенд із PostgreSQL запускається однією командою `docker compose up -d --build`; усі модулі проходять статичний аналіз.
- Ендпоінти перевірено вручну через Swagger UI (`/api-docs`) та наскрізними запитами до API з PostgreSQL у Docker Compose (реєстрація, CRUD, ролі, коди 401/403/404/409/422).
- Автоматизованих тестів ще немає. План на Лабораторну роботу 6:
  - Модульні тести для схем валідації Pydantic та обчислення порядку карток.
  - Інтеграційні тести ендпоінтів через `TestClient` (FastAPI) проти тестової бази PostgreSQL; інтерфейси репозиторіїв дозволяють підставити тестові реалізації для модульних тестів роутерів.
  - Тести безпеки для перевірки матриці ролей (кандидат vs ментор vs адмін).
  - Регресійний тест для виправлення відповіді `422` (див. розділ 6).
