# ADR-002: Вибір архітектури Backend та Бази Даних (RESTful FastAPI + Postgres)
**Статус:** Затверджено
**Дата:** 2026-09-21

### Контекст
Для серверної частини необхідна архітектура, яка дозволить максимально швидко розробити MVP. Команда має експертизу в побудові класичних API. Дані нашого додатку (користувачі, вакансії, дошки) мають чітку структуру та багато зв'язків. У нас немає високонавантажених вимог, що вимагали б горизонтального масштабування.

### Рішення
Використовувати **RESTful API** для комунікації між клієнтом і сервером, а як сховище даних обрати **реляційну базу даних Postgres**.

### Наслідки
*   **Плюси:** Висока швидкість розробки завдяки ознайомленості команди з REST; реляційний формат ідеально підходить для наших структурованих пов'язаних даних.
*   **Застереження:** Будь-яка зміна структури даних вимагатиме міграцій; можливий overfetching при роботі з REST.
*   **Мінуси:** Реляційну базу складніше масштабувати горизонтально (sharding) у порівнянні з NoSQL, якщо навантаження стрімко зросте.

### Відхилені альтернативи
1.  **NoSQL бази даних (напр., MongoDB):** Відхилено. Нам не потрібна горизонтальна масштабованість, заради якої часто беруть NoSQL. Крім того, зберігати наші сутності зручніше в реляційному форматі, а не у вигляді документів.
2.  **GraphQL:** Відхилено через вищий поріг входу; швидкість розробки MVP за допомогою REST для команди буде вищою.
