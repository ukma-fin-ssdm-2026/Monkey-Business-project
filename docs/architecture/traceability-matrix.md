# Матриця простежуваності архітектури (Traceability Matrix)

Цей документ забезпечує архітектурну простежуваність (traceability) системи **Tech Interview Board**, пов'язуючи функціональні та нефункціональні вимоги, зафіксовані в [requirements.md](../requirements/requirements.md) та [user-stories.md](../requirements/user-stories.md), з компонентами системи, зафіксованими в [high-level-design.md](high-level-design.md), відповідними архітектурними рішеннями ([ADR](decisions/)) та методами їхньої практичної верифікації.

> **Головне правило архітектурної цілісності:**
> *Жодної вимоги без компонента, жодного компонента без вимоги.*  
> Ланцюжок простежуваності: **Вимога → Архітектурний компонент → Проєктне рішення (ADR) → Метод верифікації**.

---

## 1. Реєстр архітектурних компонентів

Згідно з [high-level-design.md](high-level-design.md), система реалізується за клієнт-серверною архітектурою з монолітним бекендом і містить такі базові компоненти:

| ID компонента | Назва компонента | Технологічний стек | Роль і призначення в системі |
|---|---|---|---|
| **COMP-1** | `Frontend App` | React, PWA, Service Worker | Інтерактивний користувацький веб-інтерфейс, підтримка офлайн-роботи (PWA), управління клієнтським станом (Kanban Board UI) |
| **COMP-2** | `Backend API` | Python FastAPI (RESTful API) | Центральний модуль бізнес-логіки: автентифікація/авторизація (JWT/RBAC), CRUD-ендпоінти, планувальник дедлайнів, бізнес-правила |
| **COMP-3** | `Database` | PostgreSQL | Реляційне сховище структурованих даних (користувачі, ролі, дошки, вакансії, етапи, коментарі, звернення підтримки) |
| **COMP-4** | `Моніторинг та Аналітика` | Prometheus + Grafana | Збір інфраструктурних метрик бекенду та БД, візуалізація стану та затримок |
| **COMP-5** | `Зовнішні сервіси` | Gemini API, Email Notification Service | Інтеграція зі сторонніми сервісами для генерації питань співбесіди (AI) та розсилки email-запрошень і нагадувань |

## 5. Сценарії атрибутів якості (Quality Attribute Scenarios)

Для оцінки стійкості архітектурних рішень сформульовано 3 деталізовані сценарії атрибутів якості за стандартом SEI (Software Engineering Institute):

### Сценарій 1: Продуктивність (Performance efficiency) — PERF-1
* **Джерело стимулу (Source of stimulus):** Одночасна активність 20 зареєстрованих користувачів (кандидатів).
* **Стимул (Stimulus):** Користувачі одночасно відправляють HTTP GET-запити на завантаження своїх Канбан-дошок, кожна з яких містить 100 карток вакансій з нотатками та посиланнями.
* **Артефакт (Artifact):** `Backend API` (Board Controller), `Database` (PostgreSQL).
* **Середовище (Environment):** Нормальний режим роботи системи під піковим прогнозованим навантаженням.
* **Реакція системи (Response):** 
  1. Backend API приймає вхідні запити в асинхронному режимі (ASGI).
  2. Запити виконуються до PostgreSQL через попередньо відкритий пул з'єднань.
  3. Вибірка карток здійснюється за індексованим полем `user_id` без виконання N+1 запитів.
  4. Клієнт отримує JSON payload і монтує віртуалізований список карток.
* **Міра реакції (Response measure):** 
  - Час повного завантаження та візуалізації Канбан-дошки у браузері становить <= 1.0 секунди для всіх користувачів.
  - 95% API-запитів до бекенду повертають статус 200 OK з latency <= 200 мс (згідно з PERF-2).

### Сценарій 2: Безпека (Security) — SEC-3
* **Джерело стимулу (Source of stimulus):** Авторизований користувач у ролі Ментора (або зловмисник, що перехопив токен ментора).
* **Стимул (Stimulus):** Спроба виконати несанкціоновану операцію: виклик HTTP-методу `DELETE /api/cards/42` або `PUT /api/cards/42` для зміни чи видалення картки кандидата.
* **Артефакт (Artifact):** `Backend API` (RBAC Security Middleware / Dependency Injection).
* **Середовище (Environment):** Будь-яке робоче середовище (Production або Staging).
* **Реакція системи (Response):** 
  1. Серверний обробник перевіряє валідність JWT-токена та витягує ідентифікатор ролі (`role="mentor"`).
  2. Модуль контролю доступу (RBAC Guard) виявляє, що права на виконання операцій мутації карток належать виключно власнику дошки (`Candidate`).
  3. Запит негайно блокується до звернення до бізнес-сервісів або бази даних.
  4. Інцидент фіксується в журналі безпеки бекенду.
* **Міра реакції (Response measure):** 
  - Жодні дані картки в базі даних не змінюються і не видаляються.
  - Клієнту повертається статус-код `403 Forbidden` із поясненням причини відмови.
  - Час формування відмови становить <= 30 мс.

### Сценарій 3: Надійність (Reliability) — REL-2
* **Джерело стимулу (Source of stimulus):** Кандидат, що працює з дошкою в умовах нестабільного або повністю відсутнього інтернет-з'єднання.
* **Стимул (Stimulus):** Кандидат перетягує 3 картки вакансій в інші колонки та додає нову нотатку під час обриву зв'язку з мережею.
* **Артефакт (Artifact):** `Frontend App` (React PWA, Service Worker, Local State Sync).
* **Середовище (Environment):** Офлайн-режим (Network Outage / Disconnected).
* **Реакція системи (Response):** 
  1. Service Worker перехоплює невдалі мережеві виклики і не показує браузерну помилку збою мережі.
  2. Локальний стан інтерфейсу оновлюється миттєво (Optimistic UI).
  3. Мутаційні операції зберігаються у черзі відкладених запитів (IndexedDB).
  4. Користувачу відображається ненав'язливий індикатор: *«Офлайн-режим. Зміни збережено локально»*.
  5. При відновленні з'єднання (подія `window.online`) Service Worker у фоні відправляє накопичені операції на бекенд у правильному хронологічному порядку.
* **Міра реакції (Response measure):** 
  - 100% локально виконаних дій успішно синхронізуються із базою даних PostgreSQL після відновлення зв'язку.
  - Користувач не втрачає жодних внесених даних і не бачить блокуючих модальних вікон про помилки мережі.

## 6. Зворотна простежуваність: Компоненти ↔ Вимоги (Перевірка повноти)

Для гарантії принципу *«жодного компонента без вимоги»* нижче наведено перевірку обґрунтованості кожного вузла архітектури:

| Компонент | Обґрунтування присутності (покриті вимоги) | Чи є компонент надлишковим? |
|---|---|---|
| **COMP-1: `Frontend App`** | US-001 – US-008, 16 FRs (FR-001, FR-003, FR-004, FR-005, FR-007, FR-008, FR-009, FR-011, FR-013, FR-016, FR-017, FR-019, FR-020, FR-021, FR-023, FR-025), PERF-1, PERF-3, PERF-4, REL-2, USAB-1, USAB-2 | **Ні**, забезпечує інтерфейс користувача та клієнтську логіку Канбан-дошки |
| **COMP-2: `Backend API`** | US-001 – US-008, усі 26 FRs (FR-001 – FR-026), PERF-1, PERF-2, PERF-3, REL-1, REL-3, SEC-1, SEC-2, SEC-3 | **Ні**, реалізує обов'язкову бізнес-логіку, авторизацію та API-маршрути |
| **COMP-3: `Database`** | US-001 – US-008, 20 FRs (FR-001, FR-003 – FR-008, FR-010 – FR-013, FR-015, FR-016, FR-018, FR-019, FR-022 – FR-026), PERF-1, SEC-1 | **Ні**, забезпечує персистентне зберігання структурованих сутностей системи |
| **COMP-4: `Моніторинг та Аналітика`** | FR-026, REL-1, PERF-2, [ADR-003](decisions/ADR-003.md) | **Ні**, гарантує контроль за безвідмовністю >= 99% та виявлення затримок |
| **COMP-5: `Зовнішні сервіси`** | US-002, US-004, FR-012, FR-016, FR-022, REL-3 | **Ні**, забезпечує генерацію відповідей AI та доставку нагадувань на email |

> **Висновок перевірки:** Усі 5 компонентів системи безпосередньо обґрунтовані функціональними та нефункціональними вимогами (жодного надлишкового архітектурного блоку немає). Перевірка зворотного напрямку — «жодної вимоги без компонента» — для FR наведена в Розділі 3 (усі 26 вимог мають компонент).
