# Архітектурні рішення (Architecture Decision Records)

Цей документ містить ключові архітектурні рішення (ADR), прийняті під час розробки системи.

---

## ADR-001: Вибір архітектури Frontend-додатку (React + PWA)
**Статус:** Затверджено  
**Дата:** 2026-09-21

### Контекст
Для розробки користувацького інтерфейсу нашого додатку необхідна технологія, що дозволить створити динамічну Канбан-дошку. Ключовою вимогою (REL-2) є підтримка офлайн-синхронізації та збереження працездатності при перебоях з мережею, що вимагає ефективного управління станом (state) на стороні клієнта.

### Рішення
Використовувати бібліотеку **React** для побудови інтерфейсу у комбінації з технологією **PWA (Progressive Web App)**.

### Наслідки
*   **Плюси:** Ефективне управління станом (state) Канбан-дошки; PWA дозволяє кешувати ресурси та підтримувати роботу додатку офлайн (через Service Workers); PWA можна встановити на телефон як нативний застосунок.
*   **Застереження:** Необхідно ретельно продумати механізм синхронізації локального стану з сервером після виходу з офлайну.
*   **Мінуси:** Збільшений розмір бандлу для першого завантаження; дещо складніше SEO.

### Відхилені альтернативи
1.  **Vanilla JS / jQuery:** Відхилено, оскільки реалізація складного управління станом Канбан-дошки "з нуля" буде занадто довгою і важкою в підтримці.
2.  **Нативні мобільні додатки (iOS/Android):** Відхилено через надмірні витрати часу. Технології PWA повністю достатньо, щоб покрити наші потреби в офлайн-роботі.

## ADR-002: Вибір архітектури Backend та Бази Даних (RESTful + Postgres)
**Статус:** Затверджено
**Дата:** 2026-09-21

### Контекст
Для серверної частини необхідна архітектура, яка дозволить максимально швидко розробити MVP. Команда має експертизу в побудові класичних API. Дані нашого додатку (користувачі, вакансії, дошки) мають чітку структуру та багато зв'язків. У нас немає високонавантажених вимог, що вимагали б горизонтального масштабування.

### Рішення
Використовувати **RESTful API** для комунікації між клієнтом і сервером, а як сховище даних обрати **реляційну базу даних Postgres**.

### Наслідки
*   **Плюси:** Висока швидкість розробки завдяки ознайомленості команди з REST; реляційний формат ідеально підходить для наших структурованих пов'язаних даних.
*   **Застереження:** Будь-яка зміна структури даних вимагатиме міграцій; можливий overfetching при роботі з REST.
*   **Мінуси:** Реляційну базу складніше масштабувати горизонтально (sharding) у порівнянні з NoSQL, якщо навантаження стрімко зросте.

### Відхилені альтернативи
1.  **NoSQL бази даних (напр., MongoDB):** Відхилено. Нам не потрібна горизонтальна масштабованість, заради якої часто беруть NoSQL. Крім того, зберігати наші сутності зручніше в реляційному форматі, а не у вигляді документів.
2.  **GraphQL:** Відхилено через вищий поріг входу; швидкість розробки MVP за допомогою REST для команди буде вищою.

## ADR-003: Вибір системи моніторингу (Prometheus + Grafana)
**Статус:** Затверджено
**Дата:** 2026-09-21

### Контекст
Для забезпечення надійності системи та тестування додатку нам необхідно збирати технічні метрики (завантаження ресурсів, кількість запитів) і мати можливість графічного відображення для зручного аналізу.

### Рішення
Використовувати **Prometheus** для збору метрик та **Grafana** для їх графічного відображення.

### Наслідки
*   **Плюси:** Grafana надає найкращі інструменти для графічної візуалізації; Prometheus є стандартом індустрії з потужною системою алертів.
*   **Застереження:** Необхідно налаштувати експортери на бекенді та БД.
*   **Мінуси:** Додаткові витрати ресурсів сервера на роботу моніторингу; потрібно вивчати мову запитів PromQL.

### Відхилені альтернативи
1.  **ELK Stack (Elasticsearch, Logstash, Kibana):** Відхилено. ELK ідеально підходить для аналізу текстових логів, але для наших потреб (виключно графічне відображення числових метрик) він є занадто "важким".
2.  **Вбудовані засоби хмарних провайдерів:** Відхилено. Щоб уникнути прив'язки до конкретного провайдера (vendor lock-in) на етапі прототипування.

## Використання ШІ

- **Інструмент:** Gemini
- **Застосування:** допомога у формулюванні та структуризації обговорених архітектурних рішень (ADR).
- **Верифікація:** зміст перевірений, відповідає архітектурним рішенням.
