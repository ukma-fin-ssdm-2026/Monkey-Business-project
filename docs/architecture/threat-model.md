# Модель загроз (Threat Model, STRIDE)

Аналіз проведено над [діаграмою розгортання](uml/deployment-diagram.png) (`uml/deployment-diagram.puml`), виробниче середовище **Tech Interview Board**. Межі довіри (trust boundaries), позначені на діаграмі:

| Межа довіри | Що перетинає |
|---|---|
| **TB-1** | Браузер (Зона 0, недовірена) ↔ сервер застосунку (Зона 1) |
| **TB-2** | Backend API ↔ PostgreSQL (Зона 2 — дані) |
| **TB-3** | Система ↔ поштовий провайдер (Зона 3) |
| **TB-4** | Система ↔ LLM-провайдер (Зона 3) |
| **TB-5** | Резервна копія БД ↔ зовнішнє сховище (Зона 3) |

Для кожної межі й ключового компонента пройдено шість категорій STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Нижче — 7 виявлених ризиків, що охоплюють усі шість категорій і торкаються найчутливіших даних, позначених у [`data-model.md`](data-model.md) (`users.password_hash`, `board_mentors.invite_token`, `cards.company/position/requirements_text`, `users.email`).

## Реєстр ризиків

|  | Компонент / межа | Категорія STRIDE | Сценарій | Оцінка | Контрзахід / прийняте рішення |
|---|---|---|---|---|---|
| **R1** | **TB-1**: браузер ↔ Backend API (автентифікація) | **Spoofing** | JWT-токен користувача викрадено (XSS у Frontend App, незахищене зберігання в `localStorage`) — зловмисник видає себе за кандидата, ментора чи адміністратора без пароля. | **Висока** | Зберігати токен у `HttpOnly` + `Secure` + `SameSite=Strict` cookie (не в `localStorage`); короткий TTL токена + ротація refresh-токена; CSP-заголовки на nginx проти XSS. SEC-2 (сесія 24 год) обмежує вікно, але не є основним захистом. |
| **R2** | Backend API ↔ клієнтська офлайн-черга (Service Worker, IndexedDB) | **Tampering** | Пристрій кандидата скомпрометовано (шкідливе розширення браузера, фізичний доступ) — зловмисник підмінює накопичені офлайн-дії (переміщення карток, зміна дедлайну) ще до синхронізації з бекендом (REL-2). | **Середня** | Backend повторно валідує кожну синхронізовану операцію на стороні сервера (власність картки, бізнес-правила), а не довіряє клієнтському стану "як є". Ніяка дія з офлайн-черги не застосовується без серверної перевірки прав. |
| **R3** | **TB-2**: Backend API ↔ PostgreSQL (аналітичні запити FR-019–FR-021) | **Tampering** (з наслідком Information disclosure) | Якщо агрегаційні SQL-запити аналітики (traceability-matrix.md, FR-020) колись реалізують через конкатенацію рядків замість параметризованих запитів ORM — можливе SQL-ін'єктування, що дає змогу змінити або прочитати чужі дані (`users.email`, `users.password_hash`, картки інших кандидатів). | **Висока** | Обов'язкове використання параметризованих запитів через SQLAlchemy/asyncpg (жодного raw string SQL з користувацьким вводом); лінтер/CI-правило, що блокує рядкову конкатенацію в SQL-шарі; рев'ю приділяє цьому окрему увагу для ендпоінтів аналітики. |
| **R4** | Backend API — адміністративні дії (FR-023 блокування користувачів, FR-024 зміна стандартних етапів) | **Repudiation** | Адміністратор блокує обліковий запис або змінює `default_stages`, але окремого журналу адмін-дій у моделі даних немає (лише поточне значення `users.is_active`) — неможливо однозначно довести, хто і коли виконав дію, якщо адміністратор це заперечить. | **Середня** | Заплановане розширення поза MVP: таблиця `audit_log` (`admin_id`, `action`, `target_id`, `timestamp`). На цей семестр — свідомо прийнятий ризик через обмежений час (Could-пріоритет за MoSCoW для розширеного адміністрування), задокументовано тут для прозорості. |
| **R5** | **TB-4**: Backend API ↔ Llm API (AI-асистент, FR-022) | **Information disclosure** | AI-асистент надсилає `requirements_text` картки (позначено як `sensitive` у data-model.md), а разом із контекстом промпту можуть потрапити й `company`/`position` — тобто дані про конкретну вакансію кандидата передаються стороньому провайдеру без явної згоди користувача. | **Висока** | Мінімізувати дані в промпті (виключити `company`/`position`, залишити лише узагальнений текст вимог); явно попередити користувача при першому виклику AI-асистента і отримати згоду; перевірити політику обробки даних провайдера Llm API перед вибором постачальника. |
| **R6** | **TB-1**: nginx / Backend API (публічні ендпоінти, напр. `/auth/login`, `/cards`) | **Denial of service** | На діаграмі розгортання немає явного обмеження частоти запитів — зловмисник надсилає масовий потік запитів на публічні ендпоінти, вичерпуючи ресурси одного VPS (Зона 1) і порушуючи REL-1 (uptime ≥ 99%). | **Середня** | Rate limiting на рівні nginx (`limit_req`) для публічних маршрутів, особливо `/auth/login`; додаткове троттлінг-обмеження на бекенді за `user_id`/IP для чутливих операцій. |
| **R7** | Backend API — RBAC Middleware (FR-014, SEC-3) | **Elevation of privilege** | Помилка в реалізації RBAC-перевірки (наприклад, пропущена залежність `Depends(require_role(...))` на новому ендпоінті) дозволяє ментору виконати мутуючу операцію — редагувати чи видалити картку кандидата, хоча SEC-3 це прямо забороняє. | **Висока** | Централізована RBAC-залежність (FastAPI `Depends`), застосована на рівні роутера, а не окремого ендпоінта, щоб новий маршрут не міг "забути" перевірку; автоматизовані тести матриці ролей у CI (вже передбачені в traceability-matrix.md) для кожного мутуючого ендпоінта; deny-by-default політика.

## Підсумок за категоріями STRIDE

| Категорія | Порушує | Кількість виявлених ризиків |
|---|---|---|
| Spoofing | автентичність | 1 (R1) |
| Tampering | цілісність | 2 (R2, R3) |
| Repudiation | невідмовність | 1 (R4) |
| Information disclosure | конфіденційність | 1 (R5) *(R3 — побічний ефект)* |
| Denial of service | доступність | 1 (R6) |
| Elevation of privilege | авторизація | 1 (R7) |

Усі шість категорій STRIDE охоплено. Найвищий пріоритет мають ризики з оцінкою **"Висока"** (R1, R3, R5, R7) — вони або торкаються автентифікаційних секретів, або відкривають прямий шлях до чужих даних чи прав.

## Звʼязок із моделлю даних

Ризики R1, R3, R4 і R5 напряму спираються на поля, вже позначені як персональні/чутливі в [`data-model.md`](data-model.md):
- `users.email`, `users.password_hash` → R1 (Spoofing через крадіжку сесії), R3 (потенційний витік через SQL-ін'єкцію).
- `board_mentors.invite_token` → додатковий вектор Spoofing/Information disclosure, аналогічний R1 (токен запрошення, що діє як bearer-секрет).
- `cards.company`, `cards.position`, `cards.requirements_text` → R5 (передача стороньому LLM-провайдеру).
- `users.is_active` (адміністрування) → R4 (відсутність журналу дій).
