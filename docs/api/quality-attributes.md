# Атрибути якості API

Кожна ціль нижче має чотири частини: число, умову, за якої ціль вважається невиконаною, спосіб реалізації і спосіб вимірювання. Цілі конкретизують нефункціональні вимоги з [`requirements.md`](../requirements/requirements.md) для поточного API (`src/api/`) і узгоджені зі сценаріями якості в [`traceability-matrix.md`](../architecture/traceability-matrix.md) та ризиками в [`threat-model.md`](../architecture/threat-model.md).

Поточний бекенд — заглушка з даними в пам'яті (`store.py`), тому для кожного атрибута окремо вказано **поточний стан**: що вже перевірено на заглушці, а що можна виміряти лише після підключення PostgreSQL і розгортання.

## Продуктивність

**Ціль:** 95-й перцентиль часу відповіді CRUD-ендпоінтів ≤ 200 мс за 20 одночасних користувачів (PERF-2; кількість користувачів — з PERF-1).

**Умова провалу:** p95 > 200 мс у п'ятихвилинному прогоні навантажувального тесту з 20 віртуальними користувачами, або хоча б одна відповідь 5xx у цьому прогоні.

**Реалізація:**
- Пагінація списку карток: `limit` за замовчуванням 20, максимум 100 (`Query(ge=1, le=100)`), тож розмір відповіді обмежений. Дошка зі 100 картками (PERF-1) завантажується одним запитом з `limit=100`.
- Асинхронний ASGI-сервер (FastAPI + uvicorn).
- Заплановано для PostgreSQL: пул з'єднань і вибірка карток за індексованим полем без N+1 запитів (сценарій 1 у traceability-matrix.md).

**Вимірювання:** навантажувальний тест у k6 проти локального сервера (`uvicorn src.api.main:app --port 3000`): 20 VU, 5 хв, суміш запитів список / створення / оновлення / переміщення. Поріг `http_req_duration: p(95)<200` записано в сценарії k6, тому прогін сам завершується з помилкою, якщо ціль не виконано.

**Поточний стан:** базовий замір на заглушці (500 послідовних запитів через `TestClient`, без мережі): p95 ≈ 2 мс для `GET` списку і `POST` створення картки. Це не навантажувальний тест, а лише підтвердження, що сам код ендпоінтів не є вузьким місцем. Прогін k6 заплановано після підключення бази даних.

## Безпека

### Валідація вхідних даних

**Ціль:** будь-який невалідний запит отримує відповідь 4xx (422 — невалідні поля, 404 — неіснуючий ресурс, 405 — непідтримуваний метод) з єдиною структурою помилки `{"error": {"code", "message", "details", "request_id", "documentation"}}`. Жоден невалідний запит не отримує 2xx або 5xx.

**Умова провалу:** хоча б одна відповідь 5xx, відповідь без поля `error.code` або відповідь 2xx на запит із набору невалідних запитів.

**Реалізація:**
- Pydantic-схеми з обмеженнями: обов'язкові `company` і `position` (1–200 символів, не з пробілів), `requirements_text` ≤ 5000 символів, `HttpUrl` для посилань (FR-009), `UUID` для ідентифікаторів, `position ≥ 0` для переміщення.
- Єдиний обробник помилок (`errors.py`): доменні помилки (`NotFoundError`, `ConflictError`) і помилки валідації повертаються в однаковому форматі з деталями по кожному полю; кожна відповідь має заголовок `X-Request-ID`.

**Вимірювання:** набір невалідних запитів у pytest (порожні та задовгі поля, некоректні UUID, URL і дати, `limit=0`, `offset=-1`, недійсний JSON, непідтримуваний метод) запускається в CI на кожен push.

**Поточний стан:** набір із 18 невалідних запитів: 17 × 422 у єдиному форматі (фільтр `status` тепер валідується через enum `CardStatus`, #82), 1 × 405. Відповідей 2xx і 5xx немає. **Ціль виконана не повністю**: 405 і запити до неіснуючих маршрутів повертають стандартне тіло FastAPI `{"detail": ...}` без поля `error.code`.

### Розмежування прав ментора

**Ціль:** 100% мутуючих запитів ментора до карток кандидата (`POST`, `PATCH`, `DELETE`, `move`) отримують 403 і не змінюють жодних даних (SEC-3, FR-014).

**Умова провалу:** хоча б один мутуючий запит з токеном ментора повертає 2xx або змінює дані картки.

**Реалізація (заплановано):** JWT-автентифікація з тривалістю сесії 24 год (SEC-2); централізована RBAC-залежність FastAPI на рівні роутера з політикою deny-by-default, щоб новий ендпоінт не міг «забути» перевірку (ризик R7); rate limiting на nginx для публічних маршрутів (ризик R6).

**Вимірювання:** автоматизовані тести матриці ролей (кандидат / ментор / адміністратор × кожен мутуючий ендпоінт) у CI.

**Поточний стан:** у заглушці немає автентифікації й ролей, тому ціль поки не перевіряється. Вона стає обов'язковою разом із реалізацією FR-001/FR-002.

## Надійність

**Ціль:** доступність API ≥ 99% за тиждень (REL-1), тобто не більше 100 хвилин сумарного простою за 7 днів.

**Умова провалу:** понад 100 хвилин сумарного простою за 7 днів. Хвилина вважається простоєм, якщо `GET /health` не повернув 200 за 2 секунди.

**Реалізація:**
- Ендпоінт перевірки стану `GET /health`.
- Очікувані помилки (неіснуючий ресурс, конфлікт) обробляються як `ApiError` і повертаються як контрольовані 4xx, а не як збій процесу.
- Заплановано: моніторинг Prometheus + Grafana з алертом на `/health` (ADR-003); автоматичний перезапуск процесу (`restart: always`).

**Вимірювання:** зовнішній моніторинг (Prometheus blackbox exporter або аналог) опитує `/health` щохвилини; доступність рахується за 7 днів.

**Поточний стан:** бекенд ще не розгорнуто (на GitHub Pages опубліковано лише документацію), тому доступність поки не вимірюється. Локально `/health` повертає 200.

## Актуальність документації

**Ціль:** опублікована специфікація OpenAPI завжди відповідає коду: `docs/api/openapi-generated.yaml` у `main` і на GitHub Pages збігається з тим, що генерує поточний код.

**Умова провалу:** після повторної генерації (`python -m src.api.main`) `git diff docs/api/openapi-generated.yaml` у гілці `main` не порожній.

**Реалізація:** специфікація генерується з анотацій коду (Code-First) при кожному запуску сервера і командою `python -m src.api.main`; workflow `deploy-api-docs.yml` повторно генерує її при кожному push у `main` перед публікацією на GitHub Pages.

**Вимірювання:** перевірка розбіжностей у CI — повторна генерація і `git diff --exit-code docs/api/`.

**Поточний стан:** специфікація в `main` побайтово збігається з тією, що генерує код; workflow публікації працює. Перевірку розбіжностей у CI ще не додано.

## Аналіз компромісів

| Атрибут | Компроміс | Вплив | Пом'якшення |
|---|---|---|---|
| Безпека (валідація) | Додаткова перевірка кожного запиту збільшує затримку | Мінімальний: увесь запит на заглушці займає ≈ 2 мс (p95) | Декларативні обмеження Pydantic без додаткових звернень до бази |
| Безпека (RBAC) | Перевірка ролі на кожному мутуючому запиті | Мінімальний | Одна централізована залежність на роутері замість перевірок у кожному ендпоінті |
| Продуктивність (пагінація) | Не більше 100 карток за запит | Для дошки зі 100 картками (PERF-1) достатньо одного запиту; більші списки потребують кількох | Більший ліміт лише для адміністративних та аналітичних запитів |
| Надійність (деталі помилок) | `details.provided_value` і `request_id` повертають клієнту частину його вводу | Ризик розкриття даних, якщо в помилку потраплять чутливі поля (`requirements_text`) | Обрізати або приховувати `provided_value` для чутливих полів у продакшні; не повертати stack trace |
| Актуальність документації | Генерація специфікації при старті сервера записує файл на диск | У продакшні з read-only файловою системою запуск може завершитися помилкою | Генерувати специфікацію лише в CI, а в продакшні вимкнути генерацію при старті |
