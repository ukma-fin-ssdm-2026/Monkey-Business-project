## 4. Співпраця та робочий процес
- Стратегія гілкування: Використовуємо GitHub Flow. Гілка main захищена - зміни вносяться лише через Pull Request.
- Практики комітів: Коміти невеликі та сфокусовані на одній зміні. Повідомлення пишуться в наказовому способі, наприклад: Add task workflow description
- Правила огляду коду: Кожен PR потребує щонайменше одного схвалення, зазвичай від автора issue. Якщо автор issue є одночасно виконавцем, рев'ю запитується в іншого учасника команди. Обов'язковою умовою злиття є проходження CI. Ревʼюер перевіряє відповідність задачі, читабельність та відсутність регресій. Зауваження по коду вирішуються автором PR - або зміною коду, або поясненням, чому зміна не потрібна.
- Робочий процес завдань: Усі завдання ведуться як GitHub Issues зі станами Open → In progress → Done → Accepted. Issue має короткий і дієвий заголовок, опис із критеріями готовності, принаймні один лейбл (setup, documentation, feature, bug, in progress, accepted, blocker) та виконавця.

## 5. Вирішення конфліктів
### План вирішення конфліктів:
- Розбіжності щодо коду або підходу спершу обговорюються в коментарях до issue або PR.
- Якщо питання не вирішується асинхронно - виносимо на найближчу командну зустріч і вирішуємо голосуванням більшості.
- Якщо консенсусу немає й після зустрічі - ескалуємо питання до викладача курсу.
- Технічні конфлікти (наприклад, конфлікт злиття гілок) вирішує автор гілки за консультацією з ревʼюером.

## 7. Етична та професійна поведінка
### Спільні принципи:
- Усі учасники дотримуються правил академічної доброчесності НаУКМА та Кодексу етики ACM.
- Учасники не плагіатять код чи документацію - весь запозичений матеріал підписується та посилається на джерело.
- Учасники ставляться одне до одного з повагою, конструктивно коментують у рев'ю та уникають особистих оцінок.
- Усі рішення, що впливають на обсяг роботи, підхід чи дедлайни, фіксуються в issue, щоб залишити прозорий слід історії проєкту.

## 8. Використання ШІ
- Інструменти: Команда може використовувати кодові асистенти та чат-моделі (Claude, GitHub Copilot, Gemini) для допомоги з написанням коду, документації та підготовки завдань.
- Правила розкриття: Використання ШІ фіксується нотаткою «Використання ШІ» в артефактах лабораторних робіт та, за потреби, в описі відповідного Pull Request чи Issue - із зазначенням інструменту та того, для чого саме він застосовувався.
- Правило верифікації: Будь-який згенерований ШІ код обов'язково проходить перегляд та проходить CI-тести перед злиттям у main. Неперевірений або непротестований згенерований код у основну гілку не потрапляє.
