## 4. Співпраця та робочий процес
- Стратегія гілкування: Використовуємо GitHub Flow. Гілка main захищена - зміни вносяться лише через Pull Request.
- Практики комітів: Коміти невеликі та сфокусовані на одній зміні. Повідомлення пишуться в наказовому способі, наприклад: Add task workflow description
- Правила огляду коду: Кожен PR потребує щонайменше одного схвалення, зазвичай від автора issue. Якщо автор issue є одночасно виконавцем, рев'ю запитується в іншого учасника команди. Обов'язковою умовою злиття є проходження CI. Ревʼюер перевіряє відповідність задачі, читабельність та відсутність регресій. Зауваження по коду вирішуються автором PR - або зміною коду, або поясненням, чому зміна не потрібна. Детальні кроки огляду та критерії готовності коду — у розділі 5.
- Робочий процес завдань: Усі завдання ведуться як GitHub Issues зі станами Open → In progress → Done → Accepted. Issue має короткий і дієвий заголовок, опис із критеріями готовності, принаймні один лейбл (setup, documentation, feature, bug, in progress, accepted, blocker) та виконавця.
- Практики інженерії вимог:
  - Користувацькі історії рецензуються перед злиттям у гілку `main` із перевіркою за критеріями INVEST та чіткістю критеріїв прийняття.
  - Нефункціональні вимоги проходять спільну верифікацію на вимірюваність (наявність кількісних метрик) та відповідність категоріям ISO 25010.
- Управління артефактами:
  - Усі документи з вимогами зберігаються виключно в каталозі `/docs/requirements/` репозиторію (не у вікі).
  - Підтримка актуальності посилань на артефакти у `README.md` покладається на Керівника документації (Documentation Lead).
## 5. Політика якості та огляду коду
### Стандарт кодування
- Основний стандарт — **PEP 8** (Python 3.12).
- Форматування виконує **black** (довжина рядка 88, налаштування в `pyproject.toml`), тому питання форматування в рев'ю не обговорюються.
- **flake8** перевіряє решту правил PEP 8 і прості помилки (`.flake8`: `max-line-length = 110`; `E203` і `W503` вимкнено для сумісності з black).
- Іменування: `snake_case` — функції, змінні й модулі; `PascalCase` — класи, зокрема Pydantic-схеми; `UPPER_CASE` — константи. Імена функцій-обробників FastAPI унікальні, бо стають `operationId` в OpenAPI та назвами MCP-інструментів.
- Документація коду: docstring модуля пояснює його призначення та покриті вимоги (FR/NFR) і містить нотатку «Використання ШІ», якщо код створено з допомогою ШІ; коментарі пояснюють неочевидні рішення й обмеження, а не переказують код; кожна кінцева точка має `summary`, `description` і описані відповіді з помилками, бо специфікація OpenAPI генерується з коду.
### Обов'язкові інструменти
| Інструмент | Що перевіряє | Де запускається |
|---|---|---|
| `black` | форматування | pre-commit, CI (`static-analysis.yml`) |
| `flake8` | стиль PEP 8, невикористані імпорти та змінні | pre-commit, CI (`static-analysis.yml`) |
| `bandit` | небезпечні патерни Python: ін'єкції, слабка криптографія, захардкоджені секрети | pre-commit, CI (`static-analysis.yml`) |
| `detect-secrets` | ключі, токени й паролі в коді (базовий список винятків — `.secrets.baseline`) | pre-commit, CI (`static-analysis.yml`) |
| Dependabot | вразливі та застарілі залежності pip і GitHub Actions | GitHub, щотижня (`.github/dependabot.yml`) |
| Перевірка дрейфу специфікації | `docs/api/openapi-generated.yaml` відповідає коду | CI (`ci.yml`) |

- Кожен учасник один раз виконує `pip install -r requirements-dev.txt` і `pre-commit install`, після чого хуки запускаються перед кожним комітом.
- Версії інструментів у `requirements-dev.txt` і `.pre-commit-config.yaml` мають збігатися: оновлення інструмента, зокрема PR від Dependabot, змінює обидва файли.
- Знахідки bandit рівня Medium і High виправляються до злиття або свідомо приймаються з обґрунтуванням у `docs/code-quality/static-analysis.md`. Позначка `# nosec` допускається лише з коментарем-поясненням і за погодженням ревʼюера.
- Сповіщення Dependabot про вразливості рівня High і Critical розглядаються на найближчій командній зустрічі: залежність оновлюється, або прийнятий ризик документується в `docs/code-quality/static-analysis.md`.
### Огляд коду колегою
1. Автор відкриває PR у `main`, посилається в описі на issue і запитує рев'ю за правилом із розділу 4.
2. Перед запитом рев'ю автор запускає `pre-commit run --all-files`; якщо змінився API — перегенеровує специфікацію (`python -m src.api.main`) і комітить її.
3. Рев'ю починається після зеленого CI (`ci.yml`, `static-analysis.yml`).
4. Ревʼюер перевіряє зміни за п'ятьма критеріями:
   - **стиль і стандарти:** іменування, форматування, коментарі;
   - **якість і підтримуваність:** читабельність, логічна структура, відсутність дублювання;
   - **безпека:** валідація вводу, перевірка ролі й доступу до дошки на кожному мутуючому ендпоінті (ризик R7 у `docs/architecture/threat-model.md`), відсутність секретів і чутливих даних у відповідях та логах;
   - **використання фреймворку:** бізнес-логіка й доступ до даних відокремлені від обробників FastAPI;
   - **документація і статичний аналіз:** docstrings, OpenAPI-анотації, результати інструментів.
5. Зауваження вирішує автор PR — зміною коду або поясненням, чому зміна не потрібна. Після щонайменше одного схвалення та зеленого CI автор зливає PR і видаляє гілку.
### Критерії готовності коду (Definition of Done)
Зміна готова до злиття, якщо:
- **Форматування:** `pre-commit run --all-files` проходить без зауважень (black, flake8, bandit, detect-secrets).
- **Тести:** нова або змінена логіка покрита автоматизованими тестами (pytest), що проходять у CI. У Лаб06 набір уже наявний: зміни перевіряють через `python -m pytest`, звіт покриття додають до репозиторію; ручна перевірка Swagger UI доповнює автоматизовані тести.
- **Документація:** OpenAPI-анотації оновлено, перегенеровану `docs/api/openapi-generated.yaml` закомічено, змінені рішення відображено в документах (`docs/api/api-design.md`, ADR, `README.md`), використання ШІ позначено.
- **Безпека:** немає нових знахідок bandit рівня Medium/High і секретів; вхідні дані валідуються Pydantic-схемами; мутуючі ендпоінти захищені перевіркою ролі та доступу до дошки.
- **Процес:** PR посилається на issue, має щонайменше одне схвалення, CI зелений.
### Відповідальні ролі
- **Керівник якості (Quality Lead):** підтримує конфігурацію інструментів і CI-перевірок, координує огляд коду, стежить за дотриманням Definition of Done.
- **Ревʼюер PR:** призначається для кожного PR за правилом із розділу 4, перевіряє зміни за критеріями вище й відповідає за схвалення.
- **Аналітик безпеки (Security Analyst):** розбирає знахідки bandit і сповіщення Dependabot, документує рішення в `docs/code-quality/static-analysis.md`.
- **Керівник документації (Documentation Lead):** підтримує цей розділ статуту та посилання на звіти якості в `README.md`.

Хто виконує ці ролі в поточній лабораторній роботі — у розділі 2.
