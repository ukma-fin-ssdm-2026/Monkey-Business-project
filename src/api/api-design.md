# Документація проєктування API

## Огляд архітектури

- **Базова адреса (локально):** `http://localhost:3000`
- **Стиль API:** REST
- **Технологія:** Python FastAPI, монолітний бекенд ([ADR-002](../architecture/decisions/ADR-002.md))
- **Автентифікація:** JWT Bearer-токени — **заплановано** (FR-001, SEC-2); у поточній версії кінцеві точки відкриті
- **Формат відповіді:** JSON (`Content-Type: application/json`)
- **Стратегія версіонування:** версія в шляху URL (`/v1`, `/v2`) — **заплановано**; поточна версія специфікації `0.1.0` (див. розділ «Версіонування»)
- **Інтерактивна документація:** Swagger UI — `http://localhost:3000/api-docs`
- **Специфікація OpenAPI:** `http://localhost:3000/openapi.json` та [`openapi-generated.yaml`](openapi-generated.yaml) (генерується з коду)

Дані в поточній версії зберігаються в пам'яті (`src/api/store.py`) — це заглушка для демонстрації Code-First підходу. 

## Модель ресурсів

### Ресурс Cards (картки вакансій)

- **Кінцева точка:** `/boards/{board_id}/cards`
- **Опис:** керування картками вакансій на Канбан-дошці кандидата (FR-004–FR-010)
- **Атрибути:**
  - `id` (UUID): унікальний ідентифікатор
  - `board_id` (UUID): дошка-власник
  - `stage_id` (UUID): поточний етап (стовпець) дошки
  - `company` (string, 1–200): назва компанії — обов'язкове (FR-007)
  - `position` (string, 1–200): назва позиції — обов'язкове (FR-007)
  - `vacancy_url` (URL, необов'язкове): посилання на вакансію
  - `requirements_text` (string, до 5000, необов'язкове): текст вимог
  - `deadline` (datetime, ISO 8601, необов'язкове): дедлайн тестового завдання або співбесіди (FR-010)
  - `notifications_enabled` (boolean, за замовчуванням `true`): нагадування для картки (FR-018)
  - `status` (enum): `active` | `rejected` | `offer_accepted` (FR-006)
  - `position_index` (integer ≥ 0): порядок картки в межах етапу, `0` — перша зверху (FR-005)
  - `created_at`, `updated_at` (datetime): службові мітки часу
- **Зв'язки:**
  - належить одній дошці (`board_id`) і одному етапу (`stage_id`)
  - має багато посилань на тестові завдання (Card Links)


### Ресурс Card Links (посилання на тестові завдання)

- **Кінцева точка:** `/boards/{board_id}/cards/{card_id}/links`
- **Опис:** посилання на тестові завдання, прикріплені до картки (FR-009)
- **Атрибути:**
  - `id` (UUID): унікальний ідентифікатор
  - `card_id` (UUID): картка-власник
  - `url` (URL): коректний `http(s)`-URL
  - `created_at` (datetime): час додавання
- **Зв'язки:** належить рівно одній картці. Вкладений ресурс, бо поза карткою посилання не має сенсу.

### Службовий ресурс

- `GET /health` — перевірка життєздатності сервісу (використовується моніторингом, REL-1).

### Перелік кінцевих точок

| Метод | Шлях | Призначення | Успіх | Помилки |
|---|---|---|---|---|
| `GET` | `/boards/{board_id}/cards` | Список карток (фільтри, пагінація) | 200 | 404, 422 |
| `POST` | `/boards/{board_id}/cards` | Створити картку (FR-007) | 201 | 404, 422 |
| `GET` | `/boards/{board_id}/cards/{card_id}` | Отримати картку | 200 | 404, 422 |
| `PATCH` | `/boards/{board_id}/cards/{card_id}` | Часткове оновлення, закриття картки (FR-006, FR-008) | 200 | 404, 422 |
| `DELETE` | `/boards/{board_id}/cards/{card_id}` | Видалити картку (FR-008) | 204 | 404, 422 |
| `POST` | `/boards/{board_id}/cards/{card_id}/move` | Перемістити між етапами (FR-004, FR-005) | 200 | 404, 422 |
| `GET` | `/boards/{board_id}/cards/{card_id}/links` | Список посилань картки | 200 | 404, 422 |
| `POST` | `/boards/{board_id}/cards/{card_id}/links` | Додати посилання (FR-009) | 201 | 404, 422 |
| `DELETE` | `/boards/{board_id}/cards/{card_id}/links/{link_id}` | Видалити посилання | 204 | 404, 422 |
| `GET` | `/health` | Стан сервісу | 200 | — |

## Проєктні рішення



### Семантика HTTP-методів

- **`PATCH`, а не `PUT`, для оновлення картки.** Клієнт надсилає лише змінені поля (FR-008), повна заміна ресурсу не потрібна. Цим же методом закривається картка (`status`).
- **`POST .../move` як дія-під-ресурс.** Переміщення за drag-and-drop (FR-004, FR-005) — це бізнес-операція, що змінює етап і порядок, а не проста заміна поля, тому вона винесена в окрему кінцеву точку замість перевантаження `PATCH`.
- **Вкладений ресурс `links`.** Шлях `/cards/{card_id}/links` відображає залежність: посилання існує лише в контексті картки.
- **Іменники в множині, без дієслів у шляхах** (єдиний виняток — дія `move`).
- **`DELETE` повертає `204 No Content`; повторний виклик — `404`**, а не «тиха» успішна відповідь.




### Валідація вхідних даних

Валідація — на рівні схем Pydantic (`src/api/schemas.py`), правила видно в OpenAPI:

| Поле | Правило |
|---|---|
| `company`, `position` | рядок 1–200 символів; у `PATCH` — не лише пробіли |
| `vacancy_url`, `links.url` | коректний URL (`HttpUrl`) — FR-009 |
| `requirements_text` | до 5000 символів |
| `deadline` | дата й час ISO 8601 |
| `status` | один зі значень enum `CardStatus` |
| `position_index` | ціле число ≥ 0 |
| `limit` / `offset` | 1–100 / ≥ 0 |
| `*_id` у шляху | коректний UUID |

### Автентифікація та авторизація (заплановано)

- Схема: JWT Bearer-токен у заголовку `Authorization`; ролі кандидат / ментор / адміністратор (FR-002), права ментора — лише читання й коментарі (FR-014, SEC-3).
- У поточній версії перевірка не реалізована — це свідомо відкладено до інтеграції з модулем автентифікації. Додавання не змінить шляхи й схеми, лише додасть відповіді `401`/`403` у ті самі кінцеві точки.

### Версіонування

- Стратегія: версія в шляху URL — `/v1`, `/v2` (простіше тестувати й кешувати, видно в логах).
- Поточний стан: кінцеві точки **ще не мають префікса `/v1`**; версія `0.1.0` вказана лише в метаданих OpenAPI (`info.version`). Префікс буде додано до першого стабільного релізу, після якого зміни, що ламають сумісність (видалення/перейменування полів, зміна семантики кодів), виходитимуть лише в новій мажорній версії. Додавання необов'язкових полів і нових кінцевих точок — сумісне.

## Використання ШІ

- **Інструмент:** Claude
- **Застосування:** структурування документа за зразком лабораторної та формулювання обґрунтувань проєктних рішень на основі коду в `src/api/`.
- **Верифікація:** опис ресурсів, кінцевих точок, кодів статусу й обмежень звірено з фактичним кодом API та згенерованою специфікацією `openapi-generated.yaml`.
